# Вопрос 1. Высокая нагрузка в .NET (продвинутый middle)

Две метрики, которые стоит назвать сразу:

- **Пропускная способность (throughput)** — сколько запросов в секунду держит сервис.
- **Задержка (latency)** — сколько идёт один запрос; важны «хвосты» `p95 / p99`, а не средние.

---

## 0. Что реально ждут от продвинутого middle

Ответ строится из четырёх мыслей:

1. **Не блокировать потоки** — правильно использовать async/await.
2. **Не создавать лишний мусор** — лишние аллокации нагружают GC.
3. **Не ходить в БД и по сети лишний раз** — кэш и нормальные запросы.
4. **Опираться на измерения** — смотреть на цифры, а не угадывать.

> 💡 Козырь: под нагрузкой узкое место чаще всего **не C#, а БД** (твой опыт Oracle/PostgreSQL, EF Core).

---

## 1. Асинхронность — главное

**Суть:** пока ждём I/O (БД, внешний сервис, файл), поток не занят и обслуживает другие запросы — отсюда высокая пропускная способность.

**Правило №1: async до конца.**

```csharp
// ✘ Плохо: поток застревает в ожидании
var user = GetUserAsync(id).Result;   // или .Wait()

// ✔ Хорошо
public async Task<IActionResult> Get(int id, CancellationToken ct)
{
    var user = await _service.GetUserAsync(id, ct);
    return Ok(user);
}
```

Что полезно знать:

- Компилятор делает из `async`-метода **машину состояний**; в точке `await` поток освобождается.
- `async void` — только для UI-событий, в серверном коде — нет (исключения не поймать).
- `Task.Run` «чтобы было асинхронно» на сервере не нужен — это лишняя работа.
- Независимые запросы запускать параллельно через `Task.WhenAll`.

```csharp
// ✘ Последовательно: 2 × 100 мс = 200 мс
var a = await GetAAsync(ct);
var b = await GetBAsync(ct);

// ✔ Параллельно: ~100 мс
var taskA = GetAAsync(ct);
var taskB = GetBAsync(ct);
await Task.WhenAll(taskA, taskB);
```

| Вопрос | Что ответить |
|---|---|
| Зачем `ValueTask`? | Экономит аллокацию, когда результат часто готов сразу (кэш). В обычном коде хватает `Task`. |
| Зачем `ConfigureAwait(false)`? | В библиотеках — чтобы не возвращать продолжение в исходный контекст. В ASP.NET Core своего контекста нет, поэтому там не критично. |
| Параллелизм? | Ограничивать! Неограниченный веер запросов исчерпает пул соединений к БД и обрушит задержки. |

---

## 2. Пул потоков простыми словами

Потоки переиспользуются из **пула** (по умолчанию — примерно по числу ядер). Блокировать их нельзя.

**Thread pool starvation (голодание пула):** запросы заняли все потоки и «зависли» на `.Result`/`.Wait()`,
ожидая ответа БД. Потоки заняты, но бесполезны; новые пул добавляет медленно (примерно по одному за 500 мс).
Итог — задержка в секунды при свободном CPU.

- **Признак:** растёт очередь пула и число потоков, а задержка огромная.
- **Лечение:** убрать блокирующие вызовы. Поднимать `MinThreads` — только как временная мера (это симптом, а не причина).

> Фраза: «Я не блокирую потоки пула: I/O — только асинхронно, чтобы поток не ждал, а работал».

---

## 3. Память и GC — база

Ключевая мысль: важна **не память, а скорость аллокаций**. Чем больше мусора в секунду — тем чаще работает GC
и тем больше CPU уходит не на работу.

- GC **поколенческий**: Gen0 собирается часто и дёшево, Gen2 — редко и дороже (и даёт паузы).
- Крупные объекты (массивы от ~85 КБ) попадают в **LOH** — лучше переиспользовать.
- На сервере обычно включён **Server GC**.

Откуда «лишний» мусор:

| Источник | Чем заменить |
|---|---|
| **Boxing** (`ArrayList`, упаковка struct в object) | Generic-коллекции: `List<int>` |
| Конкатенация строк в цикле | `StringBuilder` |
| Тяжёлые LINQ-цепочки в горячем коде | обычный цикл `for` |
| Исключения как поток управления | методы `Try*` (`TryParse`) |
| Частые крупные буферы | `ArrayPool<T>` |

```csharp
// ✘ ArrayList упаковывает каждый int в объект → мусор
var list = new ArrayList();
list.Add(42);

// ✔ Generic-коллекция
var list2 = new List<int>();
list2.Add(42);
```

> `Span<T>` и `ArrayPool<T>` — инструменты для горячих путей. На middle достаточно знать, что это и зачем; в обычном коде не усложнять.

## 4. Данные и кэш — где на самом деле живёт нагрузка

Сильный раздел (EF Core, Oracle/PostgreSQL, оптимизация SQL).

| Что делаю | Зачем |
|---|---|
| `AsNoTracking()` для чтения | EF не тратит CPU на отслеживание изменений |
| Проекция в DTO через `Select` | В БД уходит только нужный SQL |
| Борьба с N+1 (`Include`, проекции) | Вместо 1000 запросов — один |
| `ExecuteUpdate/ExecuteDelete` | Один UPDATE на стороне БД вместо загрузки тысяч строк |
| Индексы + `EXPLAIN ANALYZE` | Убираю Seq Scan и медленные запросы |

```csharp
// ✔ Проекция выполняется в БД, только нужные колонки, без tracking
var dtos = await _db.Users
    .AsNoTracking()
    .Where(u => u.IsActive)
    .Select(u => new UserDto(u.Id, u.Name))   // SELECT Id, Name FROM Users WHERE IsActive
    .ToListAsync(ct);
```

**Кэширование:**

- In-memory (`IMemoryCache`) — быстро, в пределах одного инстанса.
- Распределённый (`IDistributedCache`, обычно Redis) — общий для всех инстансов.
- Ошибки: нет **инвалидации** (устаревшие данные) и **cache stampede** (ключ истёк — все ломятся в БД).

**Пул соединений и backpressure:** соединения к БД — ограниченный ресурс; лишние параллельные запросы создают очередь и таймауты. Поэтому число одновременных операций ограничивают:

```csharp
private static readonly SemaphoreSlim Gate = new(8); // не более 8 сразу
await Gate.WaitAsync(ct);
try   { await ProcessOneAsync(id, ct); }
finally { Gate.Release(); }
```

## 5. Измеряемость — коротко, но обязательно

- **Latency** смотреть по `p95 / p99`, а не по среднему.
- **`dotnet-counters`** — «посмотреть живьём»: очередь потоков, скорость аллокаций, счётчики GC.
- **BenchmarkDotNet** — сравнить два варианта кода и увидеть аллокации.
- **k6** (или подобное) — нагрузочный тест: сколько реально держит.
- **`EXPLAIN ANALYZE`** (PostgreSQL) — когда тормозит БД.

Порядок разбора «тормозит под нагрузкой»:

1. Растёт p99 → смотрим `dotnet-counters`.
2. Растёт очередь потоков → ищем `.Result`/`.Wait()`.
3. Высокая скорость аллокаций / частые Gen0-Gen2 → ищем лишний мусор.
4. Ждём соединения из пула → проблема в БД или нет кэша.

> Фраза: «Сначала измеряю — baseline и узкое место (чаще БД или I/O). Потом оптимизирую и измеряю снова».

---

## 6. Готовый ответ (2–3 минуты)

**1. Асинхронность.** «Главное — не занимать поток, пока ждём I/O. Держу весь путь асинхронным: нет
`.Result` и `.Wait()`. Пока ждём БД или сервис, поток свободен и обслуживает другие запросы — отсюда
высокая пропускная способность».

**2. Потоки.** «Потоки берутся из пула, и я их не блокирую: блокировка ведёт к голоданию пула — потоки
заняты, но простаивают, задержка резко растёт. Правило: I/O только асинхронно».

**3. Память.** «Под нагрузкой важна не память, а скорость аллокаций: больше мусора — чаще GC — больше CPU
не на работу. Поэтому избегаю boxing, использую generic-коллекции и `StringBuilder`, не использую исключения
как поток управления. `Span` и пулы — точечно, где нужно».

**4. Данные и измерения.** «Узкое место чаще всего в БД. Поэтому `AsNoTracking` и проекции в EF Core, борьба
с N+1, массовые операции через set-based SQL, проверка плана запроса, плюс кэш на чтение. И всё по
измерениям: p95/p99, счётчики через `dotnet-counters`, а не «на глаз».»

---

## 7. Шпаргалка

**Четыре мысли, покрывающие вопрос:**

| Слой | Что сказать |
|---|---|
| Асинхронность | async/await до конца, без `.Result`/`.Wait()` |
| Потоки | не блокировать пул → нет thread pool starvation |
| Память | меньше аллокаций → меньше работы GC |
| Данные | кэш, проекции, `AsNoTracking`, борьба с N+1, план запроса |

**Ассоциации «проблема → приём»:**

- Поток простаивает → **async/await**.
- Пул «голодает» → убрать **блокирующие вызовы**.
- Много мусора → generic-коллекции, `StringBuilder`, меньше LINQ в горячем коде.
- Много запросов в БД → **кэш**, проекции, `AsNoTracking`, борьба с N+1.
- Перегрузка → **ограничение параллелизма** и rate limiting.
- «Где тормозит?» → **p95/p99**, `dotnet-counters`, `EXPLAIN ANALYZE`.

**Чего НЕ надо на этом уровне:** устройство GC/LOH-компакция, `IValueTaskSource`, Pipelines, native AOT,
fine-tuning GC. Достаточно знать, что это и зачем.

# Вопрос 2. Миграция DI и жизненных циклов: .NET Framework → .NET Core

## 0. Столкновение двух миров

В .NET Framework DI был **сторонним и опциональным** (Unity, Autofac, Ninject через `IDependencyResolver`),
а в .NET Core DI **встроенный и обязательный** — через Generic Host проходит всё приложение.

| Аспект | .NET Framework (MVC/WPF) | .NET Core |
|---|---|---|
| DI | не встроен, сторонний | встроенный `Microsoft.Extensions.DependencyInjection`, Generic Host |
| Получение зависимости | `new`, service locator | constructor injection |
| HttpContext | `HttpContext.Current` | `IHttpContextAccessor` |
| Конфигурация | Web.config, `ConfigurationManager` | `IConfiguration` + `IOptions*` |
| «На запрос» | `InstancePerRequest` | `Scoped` |
| Точка старта | Global.asax / OWIN | `Program` + Host |
| Валидация графа | нет | `ValidateScopes` / `ValidateOnBuild` |

## 1. Главные боли миграции

- Разбросанный `new` и статика → заводим в DI.
- **Service Locator** (`DependencyResolver.Current`) → constructor injection.
- `HttpContext.Current` больше нет → `IHttpContextAccessor`.
- Возможности сторонних контейнеров (property injection, child-контейнеры, интерцепторы) во встроенном DI отсутствуют.
- Конфигурация: `Web.config`/`ConfigurationManager` → `IConfiguration` + `IOptions*`.
- **WPF**: не было хоста → поднимали Generic Host, view-модели в DI.
- Осознанно разложить lifetimes.

## 2. Жизненные циклы

| Lifetime | Сколько живёт | Пример |
|---|---|---|
| **Transient** | каждый раз новый | мапперы, лёгкие сервисы |
| **Scoped** | один на запрос/scope | `DbContext`, репозитории |
| **Singleton** | один на приложение | конфиг, кэши, инфраструктура |

> ★ Золотое правило: **Singleton не зависит от Scoped**.

`DbContext` по умолчанию — Scoped. В фоне/консоли scope создаём сами.

## 3. Captive Dependency

Долгоживущий держит короткоживущего. Самый частый случай — **Singleton → `DbContext` (Scoped)**.

```csharp
// ✘ Singleton зависит от Scoped → captive
builder.Services.AddSingleton<ReportService>();
builder.Services.AddDbContext<AppDbContext>(o => o.UseNpgsql(cs));

public sealed class ReportService(AppDbContext db) { /* ... */ }
```

Чем плохо: рост памяти, ошибки конкурентности (`A second operation started on this context...`), «старые» данные.

Правильно — scope на операцию:

```csharp
public sealed class ReportService(IServiceScopeFactory scopeFactory)
{
    public async Task<Report> BuildAsync(CancellationToken ct)
    {
        using var scope = scopeFactory.CreateScope();
        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
        return await db.Reports.AsNoTracking().FirstAsync(ct);
    }
}
```

## 4. Как отлавливать

1. **Валидация графа на старте:**
```csharp
builder.Host.UseDefaultServiceProvider(o => { o.ValidateScopes = true; o.ValidateOnBuild = true; });
```
`ValidateScopes` ловит Singleton→Scoped; `ValidateOnBuild` проверяет весь граф при старте.

2. **Тест-«сторож»**, который резолвит все сервисы в scope.

3. **Код-ревью и правила**: Singleton — только stateless; красные флаги — `IServiceProvider`/`DbContext` в Singleton.

Симптомы в рантайме: рост памяти, ошибки конкурентности, устаревшие данные.

## 5. Приёмы

- `BackgroundService` (Singleton): **scope на каждую итерацию** через `IServiceScopeFactory`.
- `IOptions` (singleton) / `IOptionsSnapshot` (scoped) / `IOptionsMonitor` (singleton).
- `IHttpClientFactory` вместо `new HttpClient()` в Singleton.
- WPF: Generic Host + DI; VM/окна — не Singleton (иначе утечки подписок).

## 6. Готовый ответ (2–3 минуты)

1. В .NET Core DI встроенный и обязательный; незарегистрированная зависимость = падение на старте.
2. Боли: ручные `new`/статика/service locator → DI; `HttpContext.Current` → `IHttpContextAccessor`; Web.config → IOptions; WPF → Generic Host.
3. Lifetimes: Transient/Scoped/Singleton; правило — Singleton не зависит от Scoped.
4. Captive Dependency (#1 — Singleton→DbContext): ловим `ValidateScopes`/`ValidateOnBuild` + тестом; чиним через `IServiceScopeFactory`.

## 7. Шпаргалка

- Transient — новый каждый раз; Scoped — один на запрос (DbContext); Singleton — один на приложение.
- Captive = Singleton → Scoped.
- Поймать: `ValidateScopes` + `ValidateOnBuild`; тест, резолвящий всё.
- Починить: `IServiceScopeFactory.CreateScope()`; scope на операцию/итерацию.
- Ассоциации: `HttpContext.Current` → `IHttpContextAccessor`; `InstancePerRequest` → `Scoped`; `Web.config` → `IOptions*`.

# Вопрос 3. EF Core при переносе Oracle → PostgreSQL

## Что меняется при смене провайдера

EF Core не пишет SQL сам — это делает провайдер (`Oracle.EntityFrameworkCore` → `Npgsql.EntityFrameworkCore.PostgreSQL`):
диалект, трансляция LINQ, типы параметров.

| Область | Oracle | PostgreSQL |
|---|---|---|
| Пагинация | `ROW_NUMBER` / `OFFSET … FETCH` | `LIMIT … OFFSET` |
| Логический тип | `NUMBER(1)` | `boolean` |
| GUID | `RAW(16)`, `SYS_GUID()` | `uuid`, `gen_random_uuid()` |
| Пустая строка | `''` = `NULL` | `''` ≠ `NULL` |
| Регистр имён | ВЕРХНИЙ | нижний |
| Дата-время | `DATE` содержит время | `timestamp` ≠ `timestamptz` |

## Трансляция LINQ

- Смотреть SQL **до** выполнения: `ToQueryString()`; в dev — логирование Npgsql.
- Что не перевелось в SQL, EF Core выполнит **на клиенте** — медленно и незаметно.
- Оракульный raw-SQL (`NVL`, `DECODE`, `ROWNUM`, `(+)`, `CONNECT BY`) переписать: `COALESCE`, `CASE`, `LIMIT`, `LEFT JOIN`.

## Пагинация `Skip`/`Take`

- Сортировать по уникальному ключу: `OrderBy(x => x.CreatedAt).ThenBy(x => x.Id)` — иначе страницы «плавают».
- `OFFSET` читает и выбрасывает строки → глубокие страницы медленные.
- Keyset-пагинация: `WHERE (created_at, id) < (:at, :id) ORDER BY … LIMIT 20` + индекс `(created_at DESC, id DESC)`.

## Типы

- Задавать явно: `HasColumnType("uuid" | "timestamptz" | "varchar(32)")`, `HasPrecision(18,2)`, `HasConversion<string>()`.
- Время хранить в UTC (`DateTime.UtcNow`) — иначе `timestamptz` «поедет».

## Неявные приведения ломают индексы

```sql
SELECT * FROM orders WHERE user_id = $1::text;   -- ✘ Seq Scan: индекс не применим
SELECT * FROM orders WHERE user_id = $1;         -- ✔ Index Scan: типы совпали
```

- Передавать `Guid`/`DateTime`, а не строки; в raw SQL — `NpgsqlParameter` с явным `NpgsqlDbType`.
- Функция по колонке (`upper(email)`) требует функционального индекса `ON users (lower(email))`.
- Проверять по `EXPLAIN (ANALYZE, BUFFERS)` и `pg_stat_statements`, а не «на глаз».

## Готовый ответ (сжато)

«Провайдер — часть ORM: он и пишет SQL. Поэтому после перехода я проверяю не только результат, но и план.
Пагинацию перевёл на keyset по `(created_at, id)`, типы привёл к нативным (`uuid`, `boolean`, `timestamptz`,
`numeric(18,2)`), вычистил места, где `''` в Oracle означала то же, что `NULL`. Самый неприятный класс проблем —
приведения типов: если колонка `uuid`, а параметр приходит как `text`, Index Scan превращается в Seq Scan.
Лечится типизированными параметрами и условием, написанным ровно под индекс».

# Вопрос 4. Гибридные транзакции, ресурсы и пул соединений

## Как устроена транзакция в .NET

Транзакция (`BeginTransactionAsync` или `TransactionScope`) — это **арендованное соединение из пула +
снимок/блокировки в СУБД**, и держится она до коммита. Всё остальное — следствия.

## Что ломается, если внутри транзакции есть внешние вызовы

| Что происходит | Чем грозит |
|---|---|
| Соединение занято всё время транзакции | Пул исчерпывается, остальные запросы падают с *pool timeout* |
| В PG висит `idle in transaction` | Держится снимок → autovacuum не убирает версии → растёт bloat |
| Блокировки строк живут до коммита | Рост задержки, при разном порядке захвата — deadlock |
| Внешний вызов уже сделан, коммит упал | Рассогласование: платёж прошёл, данные не сохранены |
| `TransactionScope` + второй ресурс | Попытка 2PC/DTC, которого в контейнерах обычно нет |

**Ключевая мысль:** транзакция БД не делает атомарным вызов чужого сервиса — она лишь удерживает соединение и блокировки.

## Как правильно

1. **Транзакция — только вокруг работы с БД.** Подготовка и расчёты — до, события — после.
2. **Короткие транзакции:** `BeginTransaction` → `SaveChanges` → `Commit` за миллисекунды.
3. **Атомарные команды** вместо «прочитал-изменил-записал»: `UPDATE … WHERE qty > 0`, `INSERT … ON CONFLICT`.
4. **Оптимистичный параллелизм** (`xmin`, `rowversion`) + повтор на `40001`/`40P01`.
5. **Таймауты-предохранители:** `lock_timeout`, `statement_timeout`, `idle_in_transaction_session_timeout`.
6. **Событие — через outbox** (вопрос 10), а не отправкой внутри транзакции.

## Мониторинг

- `pg_stat_activity` по `state = 'idle in transaction'` и возрасту транзакции.
- `pg_locks` + `pg_stat_activity` — кто кого блокирует.
- Метрики пула соединений и ошибки «Timeout expired … obtaining a connection».
- Бюджет: `Max Pool Size × число инстансов ≤ max_connections − запас`.

## Готовый ответ (сжато)

«Транзакция у меня охватывает только работу с БД: сеть, расчёты и уведомления — до или после. Внутри —
миллисекунды, а не секунды. Если изменения затрагивают две системы, я не соединяю их одной транзакцией:
пишу событие в `outbox` в той же транзакции, а доставку делает воркер. Длинная транзакция с HTTP-вызовом
внутри — это исчерпанный пул, `idle in transaction`, задержанный VACUUM и блокировки строк до коммита;
лечится короткой транзакцией, атомарными командами и оптимистичным параллелизмом».

# Вопрос 5. Оптимизация SQL в PostgreSQL

## Шаги диагностики

1. **Локализовать** — время в приложении или в БД (`pg_stat_statements`, логи, трейсы).
2. **Снять реальный план** — `EXPLAIN (ANALYZE, BUFFERS)` на реальных параметрах (на проде — реплика/`ROLLBACK`).
3. **Найти дорогой узел** — по `actual time × loops`.
4. **Понять причину** — статистика, нет индекса, `Seq Scan`, функция над колонкой, мало `work_mem`, bloat, соединение.
5. **Исправить и перепроверить** — «до/после».
6. **Проверить эффект в приложении** — p95/p99.

## Что искать в EXPLAIN (ANALYZE, BUFFERS)

| Поле | Что означает |
|---|---|
| `cost` / `rows` | оценка планировщика |
| `actual time` / `rows` / `loops` | факт; total ≈ `actual time × loops` |
| `rows` vs `actual rows` | главный сигнал: расхождение → плохая статистика |
| `Buffers: hit / read` | из кэша / с диска |
| `Rows Removed by Filter` | читаем лишнее |
| `Sort Method` | `Memory` ок; `external merge Disk` — мало `work_mem` |
| `Hash: Batches` | больше 1 → hash на диск |

**Красные флаги:** `Seq Scan` на большой таблице; `Nested Loop` с большим `loops`; расхождение `rows`;
`Sort`/`Hash` на диск; много `shared read`; огромный `Rows Removed by Filter`.

## Типы соединений

- **Nested Loop** — хорош при малом числе внешних строк и индексе внутри; плох при большом `loops` (O(N×M)).
- **Hash Join** — хорош для больших наборов по равенству; плох, когда хеш не влезает в `work_mem` (батчи на диск).
- **Merge Join** — хорош, когда обе стороны отсортированы; плох, когда нужна дорогая сортировка.
- Корень проблем — **неверная оценка кардинальности**.

## Что делать

`ANALYZE` / `default_statistics_target` / `CREATE STATISTICS` · индексы (составной, частичный, покрывающий,
функциональный) · убрать функции над колонками · `work_mem` · keyset-пагинация · партиционирование ·
`random_page_cost` под SSD. Подсказок планировщику в PostgreSQL нет.

## Готовый ответ (сжато)

«Локализую (`pg_stat_statements`, логи). Снимаю `EXPLAIN (ANALYZE, BUFFERS)`. Ищу узкое место по
`actual time × loops` и смотрю: расхождение `rows` и `actual rows`, тип сканирования, работу с памятью.
По соединениям: Nested Loop плох при большом числе циклов, Hash — при нехватке `work_mem`, Merge — при
дорогой сортировке; корень — в оценке кардинальности. Правлю причину (статистика, индексы, переписывание:
`ROWNUM`→`LIMIT`, `(+)`→ANSI) и замеряю «до/после»».

# Вопрос 6. Миграция Oracle → PostgreSQL

## MVCC

| Аспект | Oracle | PostgreSQL |
|---|---|---|
| Где прошлые версии | undo-сегменты | в самих таблицах (страницы) |
| Снимок по | SCN | метки `xmin`/`xmax` |
| Очистка | undo, автоматически | `VACUUM` / `autovacuum` |
| Долгий запрос | `ORA-01555` | портит горизонт vacuum |

Общее: читатели не блокируют писателей, писатели — читателей. Специфика PG: **bloat**, важность `autovacuum`.

## Блокировки

- Чтение не блокируется записью (в обеих).
- Запись — блокировка строки, второй писатель ждёт.
- В PG DDL конфликтует с чтениями (`ACCESS EXCLUSIVE`) → `CREATE INDEX CONCURRENTLY`; DDL транзакционный
  (в Oracle — авто-коммит).
- `deadlock` / `40001` → **retry**.

## Конвертация фич Oracle

- **`''` vs NULL:** в Oracle `''` = NULL; в PG `''` ≠ NULL (ломает `IS NULL`, `NOT NULL`, уникальность, конкатенацию).
- **PACKAGE:** нет аналога → схема как пространство имён; состояние сессии — temp-таблицы/`set_config` (или убирали).
- **`PRAGMA AUTONOMOUS_TRANSACTION`:** нет прямого аналога → `dblink` (отдельное соединение) или вынос логов из транзакции.
- **Типы:** `NUMBER`→`int`/`bigint`/`numeric`; `VARCHAR2`→`varchar`/`text`; **`DATE` в Oracle содержит время** → `timestamp`;
  `CLOB`/`BLOB`→`text`/`bytea`; `ROWID`→`ctid` (нестабилен).
- **Синтаксис:** `NVL`→`COALESCE`, `DECODE`→`CASE`, `ROWNUM`→`LIMIT`, `(+)`→ANSI JOIN, `CONNECT BY`→`WITH RECURSIVE`,
  `DUAL`, `seq.NEXTVAL`→`nextval()`, `MERGE`→`ON CONFLICT`; регистр идентификаторов; порядок NULL.

## План миграции

Инвентаризация → маппинг типов → конвертация PL/SQL → миграция данных (`setval`, сверки) →
**тесты эквивалентности** → сравнение производительности → настройка PG (`autovacuum`, `work_mem`, статистика) →
поэтапное переключение с откатом.

## Готовый ответ (сжато)

«MVCC в обеих даёт непересечение чтения и записи; различие — где прошлые версии. В Oracle — undo/SCN,
в PG — `xmin`/`xmax` в страницах, их убирает `VACUUM` (отсюда bloat и важность `autovacuum`). Блокировки:
строка при записи, чтение никого не блокирует; DDL в PG конфликтует с чтениями. Труднее всего: `''` ≠ NULL,
нет PACKAGE и автономных транзакций, `DATE` содержит время. Плюс массовая замена `NVL`/`DECODE`/`ROWNUM`/`(+)`/`CONNECT BY`».

# Вопрос 7. Bloat, HOT-апдейты и fillfactor

## Откуда берётся bloat

`UPDATE` в PostgreSQL не меняет строку на месте: создаётся **новая версия**, старая помечается мёртвой и ждёт
`VACUUM`. `DELETE` — так же. Если очистка не успевает, таблицы и индексы растут быстрее данных — это **bloat**.
Последствия: больше страниц на чтение того же объёма, «мягкие» индексы, долгий autovacuum, иногда планы
уходят в `Seq Scan`.

## HOT-апдейты и `fillfactor`

**HOT** (*Heap-Only Tuples*) — новые версии строк **не создают записей в индексах**. Условий ровно два:

1. ни одна из изменяемых колонок **не входит ни в один индекс**;
2. новая версия **помещается в ту же страницу** → это и обеспечивает `fillfactor` (для «горячих» таблиц 80–90 %).

Ловушка: индекс на часто обновляемой колонке (`updated_at`, `status`) **отключает HOT** — и каждый `UPDATE`
тянет за собой запись в индекс.

## Диагностика

```sql
SELECT relname, n_live_tup, n_dead_tup, n_tup_upd, n_tup_hot_upd, last_autovacuum,
       pg_size_pretty(pg_total_relation_size(relid)) AS total_size
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC LIMIT 20;
```

- Доля HOT: `n_tup_hot_upd / n_tup_upd` — близко к 1 означает «схема дружелюбна к HOT».
- Точные цифры: `pgstattuple('orders')` и `pgstatindex('idx_orders_created_at')`.
- Долгие транзакции и `idle in transaction` держат горизонт → `VACUUM` не может удалять версии (вопрос 4).

## Как лечить

- Пороги autovacuum **на уровне таблицы**: `autovacuum_vacuum_scale_factor = 0.01` и т. д.
- `fillfactor` 80–90 % для таблиц с частыми `UPDATE`.
- Не индексировать «живые» колонки; убрать лишние индексы.
- Удалять старые данные **секциями** (вопрос 8), а не миллионами `DELETE`.
- Раздутое убрать: `pg_repack` (без блокировки), `VACUUM FULL` (только в окно), `REINDEX CONCURRENTLY`.
- Из .NET: массовые изменения — `ExecuteUpdate`/`ExecuteDelete` и батчами, чтение — `AsNoTracking`, транзакции — короткие.

## Готовый ответ (сжато)

«Bloat — это пространство мёртвых версий строк и «дырок» в страницах: таблица отдаёт те же данные, но за большее
число страниц. Диагностирую по `pg_stat_user_tables` (`n_dead_tup`, `n_tup_upd`, `n_tup_hot_upd`,
`last_autovacuum`) и по `pgstattuple`; смотрю, не мешают ли очистке долгие транзакции. HOT работает при двух
условиях: изменяемые колонки не индексированы и новая версия помещается в ту же страницу — второе даёт
`fillfactor`. Поэтому я не индексирую то, что меняется постоянно, а со стороны .NET избегаю массовых `UPDATE`
ради пересчёта и держу транзакции короткими».

# Вопрос 8. Секционирование и partition pruning

## Что это

Декларативное секционирование (PostgreSQL 10+): одна логическая таблица = набор физических секций, не
пересекающихся по **ключу секционирования**.

| Стратегия | Когда выбирают |
|---|---|
| **RANGE** | Данные растут во времени; старые периоды уходят целиком (по дате) |
| **LIST** | Ограниченный набор значений: арендатор, регион, тип |
| **HASH** | Нужно равномерно разложить данные, естественного ключа нет |

## Что даёт

- **partition pruning** — отсечение секций, которые не могут содержать нужные строки;
- **дешёвое удаление** старых данных: `DETACH PARTITION` / `DROP` вместо миллионов `DELETE` (нет bloat);
- обслуживание по частям (VACUUM/ANALYZE на меньших объектах), локальные индексы, размещение по tablespace.

## Когда pruning теряется

| Условие | Pruning | Причина |
|---|---|---|
| `created_at >= :from AND created_at < :to` | да | сравнение колонки с константами того же типа |
| `date(created_at) = '2026-01-15'` | нет | функция **по колонке** |
| `created_at::text LIKE '2026-01%'` | нет | приведение колонки |
| параметр пришёл как `text` | зависит | несовпадение типов |
| фильтр не по ключу (по `user_id` при ключе по дате) | нет | индексы в PG локальные |

Из .NET это чаще всего `CreatedAt.Year`, `CreatedAt.Date`, `ToString().StartsWith(...)` и передача даты строкой.

## Как проверить

```text
✘ Append → Seq Scan on orders_2026_01 … orders_2026_12     ← читаем все секции
✔ Append + «Subplans Removed: 11» → Index Scan on orders_2026_01
```

Плюс `EXPLAIN (ANALYZE, BUFFERS)` (сколько страниц реально прочитано), `pg_stat_user_tables` по секциям и
`ToQueryString()` в самом приложении.

## Практика и EF Core

- Секции создаёт отдельное задание (например, `pg_partman`), есть `DEFAULT`-секция; отправленные/старые — удаляются.
- При миграции быстрее наполнить обычную таблицу и сделать `ATTACH PARTITION`, чем вставлять строки в партиционированную.
- EF Core секциями **не управляет**: маппим родительскую таблицу, а DDL пишем SQL-ом в миграциях.
- Уникальные ключи обязаны включать ключ секционирования: `PRIMARY KEY (id, created_at)`.

## Готовый ответ (сжато)

«Секционирование беру, когда таблица огромная и есть естественная ось — обычно RANGE по дате; LIST — по арендатору,
HASH — для равномерного распределения. Ключ выбираю по тому, как фильтруют запросы. Главный выигрыш — не только
скорость, но и обслуживание: удаление старых данных это `DETACH`/`DROP` секции вместо миллионов `DELETE`.
Pruning работает, пока условие — простое сравнение колонки с константой того же типа; как только в LINQ появляется
`CreatedAt.Year` или дата уходит строкой, в плане `Append` с `Seq Scan` по всем секциям. Проверяю через
`Subplans Removed`, `EXPLAIN (ANALYZE, BUFFERS)` и `ToQueryString()`».

# Вопрос 9. Интеграция и API: REST, gRPC, брокеры и валидация

## REST vs gRPC vs брокеры сообщений

**REST** — HTTP + JSON.

- Когда: публичный API, интеграции с внешними системами, браузер и мобильные клиенты.
- Плюсы: читается человеком, легко отладить (`curl`), штатное кэширование, работает везде.
- Минусы: текст → сериализация и лишние байты.

**gRPC** — HTTP/2 + Protobuf, контракт в `.proto`, кодогенерация клиентов.

- Когда: внутренние вызовы между своими сервисами; много и часто; нужен стриминг.
- Плюсы: компактнее и быстрее, мультиплексирование, стриминг, строгий контракт.
- Минусы: нечитаемо вручную, браузерам нужна прослойка (gRPC-Web), хуже с прокси и кэшированием.

**Брокер сообщений** (RabbitMQ, Kafka).

- Когда: долгая работа (отвечаем `202 Accepted`), пики нагрузки, события для других систем, надёжность.
- Особенности: eventual consistency; доставка «хотя бы один раз» → **дубликаты** → нужна **идемпотентность**;
  появляется инфраструктура.

| | REST | gRPC | Брокер |
|---|---|---|---|
| Формат | текст (JSON) | бинарный (Protobuf) | любой |
| Стиль | запрос → ответ | запрос → ответ (+ стриминг) | отправил и забыл |
| Ответ «сейчас» | да | да | **нет** |

**На практике — комбинация:** REST на границе с внешним миром, gRPC внутри между сервисами,
брокер — для того, что можно сделать позже.

## Валидация входных данных (ASP.NET Core)

Четыре уровня:

1. **Инфраструктура:** размер тела запроса, rate limiting, таймауты.
2. **Формат/модель:** DataAnnotations + `[ApiController]` (MVC) или endpoint-фильтр (Minimal API).
3. **Бизнес-правила:** сервисный слой, FluentValidation.
4. **Гарантия в БД:** `NOT NULL`, `UNIQUE`, `CHECK`, внешние ключи.

Коды ответов: **400** — неверный формат; **422** — нарушено бизнес-правило; **403** — нет прав;
**500** — только наша ошибка (никогда не на плохой ввод).

Практики: DTO вместо сущностей БД (защита от over-posting), ограничить `MaxRequestBodySize`,
не логировать чувствительное.

## Готовый ответ (сжато)

«Выбираю по трём вопросам: кто клиент, нужен ли ответ сейчас, насколько интенсивный обмен. Публичный API —
REST; внутренние вызовы — gRPC (Protobuf + HTTP/2, стриминг); долгие и пиковые операции — брокер: отвечаю
`202 Accepted`, работу делает воркер, обработчик идемпотентный. На практике всё три вместе. Валидация — на
четырёх уровнях: лимиты инфраструктуры → модель (DTO + `[ApiController]`/фильтр, FluentValidation) →
бизнес-правила → ограничения в БД. Плохой ввод — `400`/`422`, не `500`».

# Вопрос 10. Transactional Outbox и паттерны отказоустойчивости

## Паттерны надёжности

| Паттерн | Что решает |
|---|---|
| **Таймаут** | Не ждать бесконечно; освобождать поток и ресурсы (`HttpClient.Timeout`, `CancellationToken`) |
| **Retry + backoff + jitter** | Пережить кратковременный сбой, не устраивая «стадо» повторов |
| **Circuit breaker** | Не бомбить «лежащего» соседа и быстро падать самим |
| **Bulkhead** | Изолировать пулы: сбойный вызов не съедает все соединения |
| **Rate limiting** | Защитить себя и зависимости от перегрузки (`AddRateLimiter`) |
| **Идемпотентность** | Повтор не должен делать работу дважды (idempotency key + `UNIQUE` в БД) |

Ретрай допустим **только для идемпотентных** операций — иначе повтор платежа превращается в двойное списание.

## Проблема «событие строго после коммита»

Запись в БД и отправка в брокер — две системы без общей транзакции (**dual write**). Возможны три исхода:

- **событие потеряно** — коммит прошёл, отправка упала;
- **событие-фантом** — отправка прошла, коммит упал;
- **неизвестность** — таймаут: дошло ли? повтор даёт дубликаты, отсутствие повтора — потерю.

2PC/DTC не решение: нужен координатор и поддержка XA, в контейнерах обычно недоступен, а подготовленные
транзакции в PostgreSQL мешают `VACUUM`.

## Transactional Outbox

Сообщение пишется в таблицу `outbox` **в той же транзакции**, что и бизнес-данные. Отправляет отдельный воркер.

```text
BEGIN → INSERT orders → INSERT outbox → COMMIT     (атомарно: либо оба, либо ничего)
воркер: SELECT … FROM outbox WHERE status='new' FOR UPDATE SKIP LOCKED → publish → status='sent'
```

- Гарантия **at-least-once** → **потребитель обязан быть идемпотентным** (таблица обработанных сообщений / `UNIQUE`).
- `FOR UPDATE SKIP LOCKED` — несколько воркеров работают параллельно и не мешают друг другу.
- Повторы с backoff, после N попыток — dead-letter и алерт; отправленные записи удаляются заданием (иначе outbox сам станет источником bloat).
- Цена: задержка в один цикл воркера (сотни миллисекунд) — в обмен на надёжность.

**Альтернативы:** CDC/Debezium (читает журнал изменений), saga/процесс-менеджер с компенсациями, отправка «после
коммита» с периодической сверкой. Формула, которую стоит помнить: *exactly-once не существует из коробки →
at-least-once + идемпотентность = «эффект exactly-once»*.

## PL/pgSQL и распределённая транзакционность

- Внутри одной базы транзакционность полная: процедура атомарна, `outbox` можно писать прямо из PL/pgSQL.
- `pg_notify`/`LISTEN` — удобный «звонок» воркеру (доставка только после коммита), но **не гарантия**: нет слушателя — уведомление потеряно. Источник истины — таблица `outbox`.
- Между сервисами ACID нет: итоговая согласованность, идемпотентные шаги и компенсации (саги).

## Готовый ответ (сжато)

«Надёжность строю набором паттернов: таймауты и `CancellationToken` на все внешние вызовы, ретраи с backoff и
jitter, circuit breaker от «лежащего» соседа, bulkhead для изоляции пулов, rate limiting на входе — всё это в
resilience-пайплайне `IHttpClientFactory`. Ретраить можно только идемпотентное: ключ идемпотентности и `UNIQUE`
в БД. Чтобы событие уходило строго после коммита, использую **Transactional Outbox**: пишу сообщение в ту же
транзакцию, что и данные, а воркер забирает пачку через `FOR UPDATE SKIP LOCKED`, публикует и помечает; при
ошибке — backoff, после N попыток dead-letter с алертом. Доставка at-least-once, поэтому потребители
идемпотентны. Транзакционность PL/pgSQL работает внутри одной базы; за её пределами — саги и компенсации,
двухфазный коммит в контейнерной среде не рассматриваю».
