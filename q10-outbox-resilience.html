Отказоустойчивость и гарантия доставки событий

Retry, circuit breaker и rate limiting — и главный вопрос: как сделать так, чтобы событие ушло строго после успешного коммита в базу. Ответ — Transactional Outbox.

Алексей Грознов · ASP.NET Core, PostgreSQL, распределённые интеграции

Паттерны надёжности на бэкенде

Внешний мир ненадёжен: сеть рвётся, сервис-сосед отвечает секундами, БД берёт паузу. Задача — не «сделать так, чтобы ошибок не было», а ограничить ущерб и не превратить чужой сбой в свой отказ.

ПаттернЧто решаетКак в ASP.NET Core
ТаймаутНе ждать бесконечно: поток и downstream-ресурсы освобождаютсяHttpClient.Timeout, CancellationToken, command_timeout у Npgsql
Retry с backoff и jitterКратковременный сбой переживаем повтором, но без «стада» одновременных повторовMicrosoft.Extensions.Http.Resilience (Polly v8), AddResilienceHandler
Circuit breakerЕсли сосед «лежит», не бомбить его запросами и быстро падать самимТот же resilience-пайплайн, AddCircuitBreaker
BulkheadИзолировать пулы ресурсов: сбойный вызов не съедает все соединенияОтдельные HttpClient/пулы, лимиты параллелизма (SemaphoreSlim)

Что нельзя ретраить «вслепую»

Повтор допустим, только если операция идемпотентна. Иначе ретрай платежа превращается в двойное списание. Практика: каждый вызов несёт idempotency key, а сервер хранит его в UNIQUE-таблице и на повтор возвращает тот же результат.

Проблема «событие строго после коммита»

Обычный код выглядит логично: сохранили в базу, отправили событие в брокер. Но это две разные системы, и общей транзакции между ними нет. Поэтому «между» ними всегда есть окно, в котором что-то может пойти не так — это называют dual write (двойная запись).

Что произошлоРезультат
Коммит прошёл, отправка упалаСобытие потеряно: заказ в БД есть, а склад и почта о нём не знают. Тихо, никто не узнает
Отправка прошла, коммит упалСобытие-фантом: соседи обрабатывают то, чего в базе нет
Отправка «зависла» по таймаутуНеизвестность: дошло ли? Повтор — возможны дубликаты; не повтор — возможна потеря
Почему не «двухфазный коммит»

Идея «одной транзакции на БД и брокер» (2PC/DTC, TransactionScope + MSDTC) на практике не работает: нужен координатор и поддержка XA всеми участниками; в контейнерах и облаке DTC обычно недоступен, а подготовленные транзакции в PostgreSQL мешают VACUUM и служат источником инцидентов. Поэтому вместо «общей транзакции» используют гарантию через БД.

Transactional Outbox

Идея: сделать намерение отправить событие частью транзакции в БД. Рядом с бизнес-данными создаётся таблица outbox, и в неё пишется сообщение — в той же самой транзакции. Тогда либо есть и заказ, и событие, либо нет ни того, ни другого. Отправляет событие отдельный воркер.

Запрос клиента
   │
   ├─ BEGIN
   │    INSERT INTO orders   …
   │    INSERT INTO outbox   (payload = '{"type":"order.created","id":42}')   ← та же транзакция
   ├─ COMMIT                       ← атомарно: либо оба, либо ничего
   │
   └─ воркер: SELECT … FROM outbox WHERE status='new' FOR UPDATE SKIP LOCKED
              → отправить в брокер → UPDATE status='sent'
CREATE TABLE outbox (
    id           bigint      GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    occurred_at  timestamptz NOT NULL DEFAULT now(),
    type         text        NOT NULL,
    payload      jsonb       NOT NULL,
    status       text        NOT NULL DEFAULT 'new',   -- new | sent | failed
    attempts     int         NOT NULL DEFAULT 0,
    next_attempt timestamptz NOT NULL DEFAULT now(),   -- backoff между повторами
    sent_at      timestamptz
);
CREATE INDEX outbox_pending_idx ON outbox (next_attempt) WHERE status = 'new';
  • Гарантия — at-least-once. Событие уйдёт минимум один раз. Значит потребитель обязан быть идемпотентным: хранит id сообщения (таблица-«inbox») и игнорирует повторы.
  • Выборка пачками с FOR UPDATE SKIP LOCKED — так несколько воркеров могут работать параллельно и не мешать друг другу; порядок внутри одного ключа сохраняется, если обрабатывать по id.
  • Повторы с backoff и «мёртвая» очередь. После N неудачных попыток сообщение уходит в необработанные (dead-letter) и поднимает алерт — «застрявшее» событие должно быть видно, а не молча съедаться.
  • Очистка. Отправленные сообщения удаляют заданием по расписанию — иначе outbox сам станет источником bloat (вопрос 7).
  • Задержка. Событие уходит не «в ту же миллисекунду», а через один цикл воркера (сотни миллисекунд). Это нормальная цена: вместо мгновенности получаем надёжность.

Как это выглядит в коде и какие есть альтернативы

// 1) Продюсер: бизнес-данные и событие — в одной транзакции
await using var tx = await db.Database.BeginTransactionAsync(ct);

db.Orders.Add(order);
db.Outbox.Add(new OutboxMessage
{
    Type    = "order.created",
    Payload = JsonSerializer.SerializeToDocument(new { order.Id, order.Total })
});

await db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);      // атомарно: заказ и событие вместе

// 2) Воркер (BackgroundService): забрать пачку, отправить, отметить
var batch = await db.Outbox
    .FromSqlRaw("""
        SELECT * FROM outbox
        WHERE status = 'new' AND next_attempt <= now()
        ORDER BY id
        LIMIT 100
        FOR UPDATE SKIP LOCKED
        """)
    .ToListAsync(ct);

foreach (var msg in batch)
{
    try
    {
        await _bus.PublishAsync(msg, ct);
        msg.Status = "sent";
        msg.SentAt = DateTime.UtcNow;
    }
    catch (Exception)
    {
        msg.Attempts++;
        msg.NextAttempt = DateTime.UtcNow.AddSeconds(Math.Pow(2, msg.Attempts)); // backoff
        if (msg.Attempts >= 10) msg.Status = "failed";                          // dead-letter + алерт
    }
}
await db.SaveChangesAsync(ct);
ПодходГарантияЦена и когда выбирать
Outbox в БДAt-least-once, «не потеряется»Таблица + воркер + дедуп на стороне потребителя. Универсальный выбор, если данные уже в БД
CDC (Debezium)At-least-once, читает журнал измененийОтдельная инфраструктура (Kafka Connect). Плюс: приложение не пишет в outbox само
Saga / процесс-менеджерИтоговая согласованность + компенсацииДля длинных бизнес-процессов из нескольких сервисов; вместо «всё или ничего» — шаги и откаты
Отправка «после коммита» с ретраямиНиже: окно потери остаётсяДешевле всего; допустимо, если есть периодическая сверка (reconciliation), которая ловит расхождения
Формулировка, которую ценят на интервью

«Exactly-once доставки «из коробки» не существует. Реалистичная цель — at-least-once плюс идемпотентный потребитель, что даёт эффект exactly-once: дубликаты возможны, но последствий нет.»

PL/pgSQL и «распределённая транзакционность»

PL/pgSQL-процедура выполняется внутри одной транзакции: если внутри неё сделать COMMIT (в процедуре можно), то до этого момента либо всё, либо ничего. Это полноценная атомарность — но только внутри одной базы.

Чего PL/pgSQL сделать не может: отправить HTTP-запрос, положить сообщение в Kafka и «подождать подтверждения». Значит, граница транзакции заканчивается там же, где заканчиваются данные. Мост между «внутри БД» и «между сервисами» строится так:

CREATE OR REPLACE FUNCTION create_order(p_user uuid, p_total numeric)
RETURNS bigint LANGUAGE plpgsql AS $$
DECLARE v_id bigint;
BEGIN
    INSERT INTO orders (user_id, total, status)
    VALUES (p_user, p_total, 'new')
    RETURNING id INTO v_id;

    -- событие пишется в ТОЙ ЖЕ транзакции: атомарность сохраняется
    INSERT INTO outbox (type, payload)
    VALUES ('order.created', jsonb_build_object('id', v_id, 'total', p_total));

    -- «разбудить» воркер: уведомление доставляется только после коммита
    PERFORM pg_notify('outbox', v_id::text);
    RETURN v_id;
END $$;
  • LISTEN/NOTIFY удобен как «звонок», но не как гарантия. Уведомление приходит после коммита — это правильно (не бывает «события о том, чего нет»), но если слушателя нет, уведомление теряется. Поэтому источник истины — таблица outbox, а pg_notify лишь ускоряет реакцию воркера.
  • Между сервисами — не ACID, а сага. Длинный процесс (заказ → оплата → отгрузка) разбивается на шаги; при сбое выполняется компенсация (отменить заказ, вернуть деньги). Итоговая согласованность вместо «всё или ничего».
  • Идемпотентность — обязательное условие. Раз доставка at-least-once, каждый шаг должен быть безопасен при повторе: UNIQUE-ключ, ON CONFLICT DO NOTHING, таблица обработанных сообщений.

Готовый ответ

Какие паттерны надёжности вы внедряете на бэкенде ASP.NET Core?

«Надёжность я строю не на одном паттерне, а на наборе. Все внешние вызовы — с таймаутом и передачей CancellationToken; кратковременные сбои переживаю ретраями с экспоненциальным backoff и jitter; при устойчивой деградации соседа включается circuit breaker, чтобы мы не добивали его запросами; тяжёлые вызовы изолирую отдельными пулами (bulkhead); на входе — rate limiting, чтобы защитить и себя, и зависимости. Всё это в .NET собирается в resilience-пайплайн IHttpClientFactory. Обязательное условие для ретраев — идемпотентность операции, иначе повтор платежа приведёт к двойному списанию.»

Как гарантируете, что событие уйдёт строго после коммита в БД?

«Через Transactional Outbox. Я не пишу в брокер рядом с коммитом — это классический dual write: одна из операций может не состояться, и мы получим либо потерянное событие, либо фантом. Вместо этого в той же транзакции, что и бизнес-данные, я пишу сообщение в таблицу outbox. Отдельный воркер забирает пачку записей через FOR UPDATE SKIP LOCKED, публикует в брокер, помечает отправленные, а при ошибке увеличивает счётчик попыток и откладывает повтор с backoff. После N попыток сообщение уходит в dead-letter с алертом. Удаление отправленных настраиваю заданием, чтобы outbox не стал источником bloat.»

Как транслируется транзакционность PL/pgSQL на уровень распределённой архитектуры?

«Внутри одной базы транзакционность есть: процедура или транзакция приложения атомарна, и я могу писать outbox прямо из PL/pgSQL. Но как только в процесс вовлекаются брокер или второй сервис, ACID-транзакции между ними нет — двухфазный коммит в контейнерной среде не работает. Поэтому граница транзакции — это база, а дальше начинается итоговая согласованность: гарантия at-least-once, идемпотентные обработчики, повторы, компенсации (саги). Дополнительно pg_notify после изменения данных будит воркер, чтобы событие уходило почти сразу — при этом источником истины остаётся таблица outbox, а не уведомление.»
