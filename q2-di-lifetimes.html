Миграция DI и жизненных циклов: .NET Framework → .NET Core

Какие боли возникают при переносе внедрения зависимостей и жизненного цикла объектов, что такое Captive Dependency и как их ловить. На уровне продвинутого middle, с примерами на C#.

Алексей Грознов · разбор вопроса по резюме (перевод legacy MVC/WPF на .NET Core)

0. Столкновение двух миров

Суть ответа одной фразой: в .NET Framework внедрение зависимостей (DI) было опциональным и сторонним (Unity, Autofac, Ninject через IDependencyResolver), а в .NET Core DI стал встроенным и обязательным — через него проходит всё приложение (Generic Host). Отсюда и большинство болей при миграции: код, который раньше жил «сам по себе» (new, статика, service locator), приходится заводить в общий контейнер и следить за жизненными циклами.

Главная смена парадигмы

Раньше объект мог «достать» себе зависимость сам (создать, взять из статики или из локатора). В .NET Core зависимость должна быть зарегистрирована, иначе — ошибка на старте. Отсутствие регистрации = падение при запуске, а не «в рантайме где-то потом». Это одновременно и строже, и безопаснее.

1. Главные боли миграции DI

То, с чем реально сталкиваешься при переносе кода:

  1. Разбросанный new и статика. Зависимости создавались вручную или лежали в статических классах. Теперь всё нужно завести в DI-контейнер.
  2. Service Locator. Код вызывал DependencyResolver.Current.GetService<T>() или тянул IServiceProvider везде. Это антипаттерн — переходим на constructor injection.
  3. HttpContext.Current больше нет. Классическая боль миграции — заменяем на IHttpContextAccessor (только для инфраструктурного кода).
  4. Возможности сторонних контейнеров. Autofac/Unity умели property injection, child-контейнеры, перехватчики (interceptors). Встроенный DI это не умеет — либо упрощаем, либо подключаем Autofac рядом (Autofac.Extensions.DependencyInjection).
  5. Конфигурация. ConfigurationManager / Web.config → IConfiguration и IOptions* (у них тоже свои lifetimes).
  6. WPF отдельная история. У WPF не было встроенного хоста — приходилось поднимать Generic Host внутри WPF-приложения и заводить в DI view-модели и сервисы.
  7. Жизненные циклы. Нужно осознанно разложить всё по Transient / Scoped / Singleton и не сломать граф — об этом ниже.
Частый подводный камень

При переносе легко «потерять» Scope: код, который раньше получал объект статически, после миграции становится Singleton — и вместе с ним навсегда тянет за собой что-то «запросное» (тот же DbContext). Это и есть Captive Dependency (раздел 3).

2. Жизненные циклы: Transient / Scoped / Singleton

LifetimeЧто этоКогда брать
TransientНовый экземпляр на каждое обращениеЛёгкие сервисы без состояния (мапперы, отправители)
ScopedОдин экземпляр на HTTP-запрос (на «scope»)DbContext, репозитории, request-контекст
SingletonОдин на всё приложениеКонфиг, кэши, stateless-инфраструктура (должен быть потокобезопасен!)
★ Золотое правило

Долгоживущий сервис не должен зависеть от короткоживущего. Singleton не зависит от Scoped. Если нарушить — Scoped-объект «прилипает» к Singleton и живёт вечно. Это и есть Captive Dependency.

Lifetimes в ASP.NET Core — как выглядит на практике

builder.Services.AddTransient<IMapper, Mapper>();        // новый каждый раз
builder.Services.AddScoped<IOrderRepository, OrderRepository>(); // раз на запрос
builder.Services.AddSingleton<IClock, SystemClock>();     // один на приложение

// DbContext по умолчанию регистрируется как Scoped — это важно!
builder.Services.AddDbContext<AppDbContext>(o => o.UseNpgsql(cs));
Где «живёт» Scoped вне HTTP

В фоновых сервисах и консольных приложениях HTTP-запроса нет, поэтому scope нужно создавать самому (IServiceScopeFactory.CreateScope()). Если этого не делать — получишь либо ошибку, либо «вечный» объект.

3. Captive Dependency — суть и как проявляется

Captive Dependency — это когда сервис с большим временем жизни удерживает ссылку на сервис с меньшим временем жизни. Самый частый случай: Singleton держит Scoped (обычно DbContext).

Классический (и опасный) пример

// ✘ ReportService — Singleton, но зависит от Scoped DbContext
builder.Services.AddSingleton<ReportService>();   // время жизни: всё приложение
builder.Services.AddDbContext<AppDbContext>(o => o.UseNpgsql(cs)); // Scoped!

public sealed class ReportService(AppDbContext db) // Scoped попал в Singleton → captive
{
    public Task<Report> BuildAsync() => db.Reports.FirstAsync();
}

Чем это плохо на практике:

  • DbContext создаётся один раз и живёт всё время приложения → растёт память (накопленные отслеживаемые сущности), устаревают данные.
  • Возникают ошибки конкурентности: «A second operation started on this context before a previous operation completed» — один и тот же контекст дергают параллельно.
  • Ошибки «Cannot access a disposed object» и трудноуловимые баги.
Запомнить

Captive Dependency #1: Singleton → DbContext (Scoped). Это вопрос, который интервьюер почти наверняка ждёт услышать как «самый частый случай».

Как правильно, когда Singleton всё же нужен доступ к БД

Не инжектить DbContext и не тащить IServiceProvider, а создавать scope на операцию через IServiceScopeFactory:

Правильно: scope на каждую операцию

public sealed class ReportService(IServiceScopeFactory scopeFactory)
{
    public async Task<Report> BuildAsync(CancellationToken ct)
    {
        // Создаём свой scope и берём из него Scoped-зависимости.
        using var scope = scopeFactory.CreateScope();
        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();

        return await db.Reports.AsNoTracking().FirstAsync(ct);
    }
}

4. Как отлавливать Captive Dependency

Это ключевая часть вопроса — интервьюер хочет услышать конкретные способы, а не «ну, стараюсь быть внимательным».

Способ 1: встроенная валидация графа на старте (главный)

В .NET Core есть две опции провайдера, которые проверяют граф зависимостей при старте и падают сразу, если Singleton тянет Scoped:

Включаем проверку scope и сборки графа

builder.Host.UseDefaultServiceProvider(options =>
{
    options.ValidateScopes = true;    // ловит: Singleton -> Scoped
    options.ValidateOnBuild = true;   // ловит: незарегистрированные зависимости, ошибки графа
});
Что это даёт

ValidateScopes в момент создания Singleton-а увидит попытку получить Scoped и бросит: «Cannot consume scoped service 'AppDbContext' from singleton 'ReportService'». ValidateOnBuild проверяет весь граф при старте приложения — это ловит и captive-зависимости, и забытые регистрации. По умолчанию ValidateScopes включён только в Development — поэтому его включают во всех средах.

Способ 2: тест, который резолвит все сервисы

Дополнительная страховка в CI: построить провайдер из реальных регистраций и попытаться получить каждый сервис внутри scope. Падение теста = проблема найдена до продакшена.

Тест-«сторож» на граф DI

[Fact]
public void Di_graph_is_valid()
{
    var services = new ServiceCollection();
    ConfigureServices(services); // те же регистрации, что в приложении

    var provider = services.BuildServiceProvider(new ServiceProviderOptions
    {
        ValidateScopes = true,
        ValidateOnBuild = true
    });

    using var scope = provider.CreateScope();
    foreach (var descriptor in services)
    {
        if (descriptor.ServiceType.IsGenericTypeDefinition) continue;
        // Не должно бросать исключение для реально зарегистрированных зависимостей.
        scope.ServiceProvider.GetService(descriptor.ServiceType);
    }
}

Способ 3: код-ревью, правила и анализ

  • Правило для ревью: Singleton — только stateless/инфраструктура; всё, что ходит в DbContext — Scoped.
  • Красные флаги в коде: инжект IServiceProvider или DbContext в Singleton; хранение HttpContext в поле.
  • Roslyn-анализаторы и проверки на CI (в т.ч. правило ASP0000 — не вызывать BuildServiceProvider() в ConfigureServices).

Симптомы в рантайме (когда не поймали заранее)

  • Постоянно растущая память (captured-объекты не собираются GC).
  • Ошибки конкурентности у DbContext.
  • «Устаревшие» данные, которые должны были обновиться на следующий запрос.

5. Приёмы и код, которые стоит назвать

Фоновые сервисы (BackgroundService — это Singleton)

Scope на каждую итерацию — обязательный паттерн

public sealed class CleanupWorker(IServiceScopeFactory scopeFactory) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            using (var scope = scopeFactory.CreateScope())   // НОВЫЙ scope на итерацию
            {
                var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
                await db.CleanupAsync(ct);
            }
            await Task.Delay(TimeSpan.FromMinutes(5), ct);
        }
    }
}

Опции конфигурации и их lifetimes

  • IOptions<T> — singleton, значение на старте.
  • IOptionsSnapshot<T> — scoped, перечитывается на запрос.
  • IOptionsMonitor<T> — singleton с уведомлениями об изменениях.

Это хороший пример того, что lifetime нужно понимать осознанно, а не «на глаз».

HTTP-клиенты

Не хранить new HttpClient() в Singleton-поле (проблемы с сокетами и DNS), а брать через IHttpClientFactory — типобезопасные клиенты уже управляются фабрикой.

WPF-специфика (из опыта миграции)

  • Поднимали Generic Host внутри WPF: Host.CreateDefaultBuilder() + StartAsync на старте приложения.
  • View-модели и окна получали через DI; аккуратно с lifetimes: окно/VM обычно не Singleton, иначе накапливаются подписки на события (утечки).
  • Тяжёлые сервисы (логгеры, кэши, клиенты) — Singleton; «на экран» — Transient/Scoped.
★ Итоговая мысль раздела

При миграции DI главное — не «перенести регистрации», а осознанно разложить зависимости по lifetimes и включить валидацию, чтобы граф ломался на старте, а не в продакшене.

6. Готовый ответ (2–3 минуты)

Четыре короткие мысли — их легко запомнить и произнести.

1. Главное различие. «В .NET Framework DI был сторонним и опциональным (Unity, Autofac через IDependencyResolver), а в .NET Core DI встроенный и обязательный — через Generic Host проходит всё приложение. Если зависимость не зарегистрирована, приложение падает на старте, а не «где-то потом»».

2. Главные боли. «Перенос неявных зависимостей: ручные new, service locator, статика. Пришлось убрать HttpContext.Current → IHttpContextAccessor, перевести конфигурацию с Web.config на IOptions, а в WPF — поднять Generic Host и завести view-модели в DI».

3. Жизненные циклы. «Transient — новый на каждое обращение; Scoped — один на запрос (DbContext); Singleton — один на приложение. Золотое правило: долгоживущий не должен зависеть от короткоживущего — Singleton не зависит от Scoped».

4. Captive Dependency. «Самый частый случай — Singleton держит DbContext (Scoped). Ловил это включением ValidateScopes и ValidateOnBuild — граф падает на старте с понятной ошибкой, плюс отдельный тест, который резолвит все сервисы в scope. Починка — не тащить DbContext, а создавать scope через IServiceScopeFactory на каждую операцию; в фоновых сервисах — scope на итерацию».

★ Козырь под твой опыт

«При переводе legacy MVC/WPF на .NET Core именно настройка DI и lifetimes заняла больше всего времени: мы фактически заново выстраивали граф зависимостей и правило — что Singleton, а что Scoped, чтобы не словить captive-зависимости на DbContext».

Captive Dependency — карточка

  • Что это: долгоживущий держит короткоживущего (Singleton → Scoped).
  • Частый случай: Singleton → DbContext.
  • Симптомы: рост памяти, ошибки конкурентности у DbContext, «старые» данные.
  • Как поймать: ValidateScopes = true + ValidateOnBuild = true; тест, резолвящий все сервисы; код-ревью.
  • Как чинить: IServiceScopeFactory → CreateScope(); scope на операцию / итерацию.

Быстрые ассоциации «боль → решение»

  • Ручные new и статика → завести в DI (constructor injection).
  • HttpContext.Current → IHttpContextAccessor.
  • Web.config → IConfiguration + IOptions*.
  • InstancePerRequest → Scoped.
  • Singleton нужен доступ к БД → IServiceScopeFactory + CreateScope().
  • Боюсь сломать граф → ValidateScopes/ValidateOnBuild + тест.

Чего НЕ надо на этом уровне

Достаточно знать по верхам: различия keyed-сервисов, кастомные IServiceProvider, декораторы через сторонние контейнеры, source generators для DI. Уверенно рассказать базу (lifetimes + captive + валидация) важнее, чем блеснуть деталями.
