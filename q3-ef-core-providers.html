EF Core: перенос с Oracle на PostgreSQL

Что меняется при смене провайдера, где перестаёт работать трансляция LINQ, как ведут себя Skip/Take и GUID/UUID — и почему неявные приведения типов «убивают» индексы.

Алексей Грознов · EF Core, Oracle → PostgreSQL, высоконагруженный backend

Вопрос 3. Что вообще меняется при смене провайдера

EF Core сам SQL не пишет — он транслирует LINQ в запрос средствами провайдера. Поэтому при переезде с Oracle на PostgreSQL меняется не модель, а диалект: пакет провайдера, трансляция выражений, типы параметров и поведение по краям.

Как это формулировать на интервью

«Провайдер — часть ORM. Он переводит LINQ в конкретный диалект и определяет, какие типы CLR во что отображаются. Поэтому после смены провайдера я не верю, что «тот же LINQ даст тот же план»: смотрю сгенерированный SQL и план в самой СУБД».

LINQ → SQL: что перестаёт работать

Проблема не в LINQ, а в том, что часть выражений транслируется, а часть — нет. Что не удалось перевести в SQL, EF Core либо выполнит на клиенте (тихо и медленно), либо бросит исключение — в зависимости от версии и формы запроса.

Типичные грабли после смены провайдера

// ✘ 1) Оракульный SQL, оставшийся в коде через FromSqlRaw: в PG такого диалекта нет
var rows = await db.Orders
    .FromSqlRaw("SELECT * FROM orders WHERE NVL(status,'NEW') = 'NEW' AND ROWNUM <= 100")
    .ToListAsync();
// на PostgreSQL это COALESCE(status,'NEW') и LIMIT 100

// ✘ 2) Отсечение по дате через свойство .Date/.Year — не индексируется и мешает pruning
var jan = await db.Orders.Where(o => o.CreatedAt.Date == day).ToListAsync();

// ✔ 3) Границы диапазона вместо функции по колонке
var from = day.Date;                    // 00:00
var to   = from.AddDays(1);             // 00:00 следующего дня
var janOk = await db.Orders
    .Where(o => o.CreatedAt >= from && o.CreatedAt < to)
    .ToListAsync();
  • Проверяйте SQL, а не догадывайтесь: query.ToQueryString() показывает, что уйдёт в базу, — до выполнения запроса.
  • Настройте логи Npgsql (LogTo, EnableSensitiveDataLogging только в dev) — видно и SQL, и типы параметров.
  • Никаких «клиентских» вычислений в середине цепочки: ToList() до Where тащит всю таблицу в память.

Пагинация Skip/Take

Синтаксис в LINQ не меняется, но уходит в разный SQL:

-- Oracle
SELECT * FROM (
  SELECT o.*, ROW_NUMBER() OVER (ORDER BY created_at) rn FROM orders o
) WHERE rn BETWEEN 41 AND 60;

-- PostgreSQL
SELECT * FROM orders ORDER BY created_at LIMIT 20 OFFSET 40;
  • Без ORDER BY страница «плавает»: порядок строк в PG не определён, и клиент может увидеть одну и ту же запись дважды. Сортировка по уникальному ключу обязательна: OrderBy(x => x.CreatedAt).ThenBy(x => x.Id).
  • OFFSET дорогой: база честно читает и выбрасывает OFFSET строк, поэтому «глубокие» страницы (offset 100 000) замедляются.
  • Правильное решение — keyset-пагинация («по курсору»): вместо номера страницы передаём последний увиденный ключ.
// keyset-пагинация: WHERE (created_at, id) < (:lastAt, :lastId) ORDER BY created_at DESC, id DESC LIMIT 20
public Task<List<Order>> NextPage(DateTime lastAt, Guid lastId) =>
    db.Orders
      .Where(o => o.CreatedAt < lastAt || (o.CreatedAt == lastAt && o.Id.CompareTo(lastId) < 0))
      .OrderByDescending(o => o.CreatedAt).ThenByDescending(o => o.Id)
      .Take(20)
      .ToListAsync();

Работает O(1) по индексу (created_at DESC, id DESC) независимо от глубины — и одинаково хорошо на Oracle и на PostgreSQL.

Соответствие типов задают явно — иначе провайдер выберет сам, а «сам» не всегда совпадёт с тем, что уже лежит в существующей таблице:

protected override void OnModelCreating(ModelBuilder b)
{
    b.Entity<Order>(e =>
    {
        e.Property(x => x.Id).HasColumnType("uuid");
        e.Property(x => x.CreatedAt).HasColumnType("timestamptz");   // время с часовым поясом
        e.Property(x => x.Total).HasPrecision(18, 2);          // numeric(18,2)
        e.Property(x => x.Status).HasColumnType("varchar(32)");
        e.Property(x => x.Kind).HasConversion<string>();       // enum как строка
    });
}

Для timestamptz в .NET всегда храните время в UTC (DateTime.UtcNow, а не Now) — иначе один и тот же момент «поедет» при смене таймзоны сервера.

Неявные приведения типов и почему падают индексы

Это главный практический риск при миграции. Индекс в PostgreSQL работает, когда тип параметра совпадает с типом колонки. Если запрос приводит колонку к другому типу, планировщик не может применить индекс — и делает Seq Scan по всей таблице.

-- колонка user_id имеет тип uuid, а параметр приходит как text
SELECT * FROM orders WHERE user_id = $1::text;   -- ✘ Seq Scan: индекс не применим
SELECT * FROM orders WHERE user_id = $1;         -- ✔ Index Scan: типы совпали
  • Откуда берётся text: в метод пришла string вместо Guid; параметр добавлен без типа; FromSqlRaw с интерполяцией значений.
  • Функции по колонке работают так же: WHERE upper(email) = … не использует индекс по email. Для такого условия нужен функциональный индекс CREATE INDEX … ON users (lower(email)) — и условие в запросе должно выглядеть точно так же.
Как поймать проблему, а не надеяться
  • ToQueryString() — увидеть, что уходит в базу, до выполнения.
  • EXPLAIN (ANALYZE, BUFFERS) — Seq Scan там, где ждали Index Scan, плюс строка Filter с приведением.
  • pg_stat_statements — какие запросы реально дорогие.
  • Типизированные параметры: Guid/DateTime вместо строк, а в raw SQL — NpgsqlParameter с явным NpgsqlDbType.

Чек-лист проверки после смены провайдера

  1. Сменить пакет провайдера и UseOracle → UseNpgsql; проверить, что миграции собирают ту же схему.
  2. Прогнать тесты с логированием SQL: ищем клиентскую оценку, лишние «N+1» и неожиданные приведения.
  3. На горячих запросах снять EXPLAIN (ANALYZE, BUFFERS) и убедиться, что индексы работают.
  4. Сверить типы схемы и модели: uuid, boolean, timestamptz, точность numeric.
  5. Проверить логику, где «пустая строка = NULL» была нормой (в Oracle) и перестала ею быть в PG.
  6. Перевести глубокую пагинацию на keyset.

Готовый ответ

Да, сталкивался: EF Core — это LINQ, а SQL пишет провайдер.

«При переносе с Oracle на PostgreSQL я в первую очередь перестроил ожидания: меняются не запросы в коде, а трансляция в SQL. Поэтому каждый горячий запрос я проверял через ToQueryString() и EXPLAIN: после смены диалекта часть выражений перестаёт переводиться в SQL и начинает выполняться на клиенте.»

Что нашёл конкретно.

«Пагинация: Skip/Take без сортировки по уникальному ключу давала «плавающие» страницы и дубликаты — перевёл глубокие страницы на keyset-пагинацию по (created_at, id). Типы: привёл модель к нативным типам PG — uuid, boolean, timestamptz, numeric(18,2) вместо оракульных RAW(16) и NUMBER(1). И отдельно вычистил места, где в Oracle '' означала то же, что NULL: в PostgreSQL это разные значения, а логика фильтров на этом держалась.»

Про неявные приведения и индексы.

«Самая неприятная находка — приведения типов. Если колонка uuid, а параметр приходит как text, PostgreSQL сравнивает преобразованные значения, индекс становится неприменим — и в плане появляется Seq Scan. То же с функциями по колонке: where upper(email) не использует индекс по email, для него нужен функциональный индекс по lower(email). Рецепт: передавать типизированные параметры (Guid, а не string), в raw SQL задавать NpgsqlDbType, а условие писать ровно так, как объявлен индекс. И проверять это по плану, а не на глаз.»
