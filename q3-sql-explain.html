Тормозит критический эндпоинт: сложный SQL из Oracle

Пошаговый разбор: как найти проблему, что смотреть в EXPLAIN (ANALYZE, BUFFERS) и когда Hash / Merge / Nested Loop становятся узким местом.

Алексей Грознов · курсы QPT-PostgreSQL, DBA2, DBA3 (PostgresPro)

Вопрос 3. План действий по шагам

Принцип: сначала измерить и локализовать, потом менять. Никогда не «оптимизировать наугад» — тем более запрос, перенесённый из Oracle, где его план был другим.

  1. Убедиться, что тормозит именно SQL. Смотрим, где уходит время эндпоинта: приложение, сеть, сериализация или БД. По базе — pg_stat_statements (наибольшие total_exec_time / mean_exec_time), логи (log_min_duration_statement), трейсы APM.
  2. Снять реальный план. EXPLAIN (ANALYZE, BUFFERS) на реальных параметрах: план зависит от значений. ANALYZE реально выполняет запрос — на проде осторожно (реплика или транзакция с ROLLBACK).
  3. Найти дорогой узел. В дереве плана — узлы с наибольшим actual time × loops. Часто один-два узла «съедают» почти всё время.
  4. Понять причину. Обычно: устаревшая статистика (плохая оценка кардинальности), отсутствие индекса, Seq Scan на большой таблице, функция/приведение над колонкой в WHERE, мало памяти под сортировку/хеш, bloat, неудачный тип соединения.
  5. Исправить и перепроверить. Индекс, статистика, переписанный запрос, настройки — и снова план. Сравнить «до/после» по плану и по реальной нагрузке.
  6. Проверить эффект в приложении. Что упала задержка эндпоинта (p95/p99), а не только «время запроса в консоли».

Как найти «виновника» среди запросов

SELECT query, calls, mean_exec_time, total_exec_time
FROM   pg_stat_statements
ORDER  BY total_exec_time DESC
LIMIT  20;
Отдельная проблема миграции из Oracle

В перенесённом запросе часто осталась «оракловская» логика: (+), ROWNUM, NVL/DECODE, неявные преобразования типов, hints. В PostgreSQL подсказок нет, а неявные преобразования убивают использование индексов.

Что искать в EXPLAIN (ANALYZE, BUFFERS)

План — дерево узлов: у каждого есть оценка планировщика и, при ANALYZE, — факт. Смысл в сравнении этих чисел.

Пример вывода (фрагмент)

Hash Join  (cost=1120.5..9430.1 rows=50 width=40)
           (actual time=8.311..402.774 rows=50 loops=1)
  Buffers: shared hit=20114 read=5832
  ->  Seq Scan on orders o  (cost=0.00..8000.0 rows=5000 width=24)
                             (actual time=0.02..380.9 rows=480000 loops=1)
        Filter: (status = 'NEW'::text)
        Rows Removed by Filter: 4520000
  ->  Hash  (actual time=8.1..8.1 rows=200 loops=1)
        Buckets: 1024  Batches: 4  Memory Usage: 1024kB
Sort Method: external merge  Disk: 25120kB
Planning Time: 1.204 ms
Execution Time: 405.771 ms

Здесь сразу три «красных флага»: Seq Scan с огромным Rows Removed by Filter, Batches: 4 у Hash (не хватило памяти) и сортировка на диск (external merge Disk).

  • Оценка строк расходится с фактом (в разы/порядки).
  • Sort / Hash на диск (external merge, Batches > 1).

Типы соединений: когда они становятся узким местом

Способ соединения не «плохой» сам по себе — плохим его делает несоответствие данным. Планировщик выбирает его по оценке кардинальности; ошиблась оценка — ошибётся и выбор.

Nested Loop

  • Хорош: внешних строк мало, внутренний поиск по индексу.
  • Плох: внешних строк много → тысячи циклов, сложность O(N×M).
  • Сигнал: большое loops; rows на внешнем узле в разы меньше actual rows.

Hash Join

  • Хорош: большие наборы, соединение по равенству.
  • Плох: хеш не влезает в work_mem → батчи на диск.
  • Сигнал: Batches больше 1, рост Memory Usage / temp written.

Merge Join

  • Хорош: обе стороны уже отсортированы (индексами).
  • Плох: нужна дорогая сортировка больших наборов (уходит на диск).
  • Сигнал: узлы Sort с external merge Disk перед Merge Join.
ТипПодходитПроблема
Nested LoopМало внешних строк + индекс внутриМного строк → O(N×M)
Hash JoinБольшие наборы по равенствуНе хватило памяти → диск
Merge JoinОбе стороны отсортированыДорогая сортировка
★ Ключевая мысль

«Плохой» — не тип соединения, а неверная оценка кардинальности. Если планировщик думает, что строк 10, он выберет Nested Loop; если на деле их 500 000 — это катастрофа. Поэтому сначала сравнивают rows и actual rows, и только потом — соединения.

Настройки, которые реально влияют

  • work_mem — память на сортировки и хеши (умножается на число операций).
  • random_page_cost — для SSD ниже (≈1.1), иначе индексы недооцениваются.
  • effective_cache_size — «сколько данных примерно в кэше».
  • enable_seqscan и т. п. — только для диагностики.
Чего в PostgreSQL нет

Подсказок планировщику (как /*+ INDEX(...) */ в Oracle). Есть pg_hint_plan, но правильнее починить статистику и индексы, а не «заставлять» план.

Готовый ответ (сжато)

«Сначала локализую: время уходит в приложении или в БД (pg_stat_statements, логи, трейсы). Затем снимаю EXPLAIN (ANALYZE, BUFFERS) на реальных параметрах. Узкое место ищу по actual time × loops и смотрю три вещи: расхождение rows и actual rows (плохая статистика → неверный план), тип сканирования (Seq Scan там, где нужен индекс) и работу с памятью (сортировки/hash на диск). По соединениям: Nested Loop плох при большом числе циклов, Hash — при нехватке work_mem, Merge — при дорогой сортировке; но корень обычно в оценке кардинальности. Дальше правлю причину: статистика, индексы, переписывание запроса (ROWNUM → LIMIT, переписать (+)-джойны), при необходимости work_mem и партиционирование. И обязательно замеряю «до/после» на реальной нагрузке».
