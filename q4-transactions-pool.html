Гибридные транзакции: соединение, пул и блокировки

Почему транзакция с вызовом внешнего сервиса внутри — это бомба под пул соединений, что происходит с блокировками в PostgreSQL и как удерживать соединение минимальное время.

Алексей Грознов · серверная логика на .NET, PostgreSQL, высокие нагрузки

Как устроена транзакция в .NET

В EF Core есть два способа начать транзакцию — оба держат одно соединение к БД, пока транзакция не завершена:

// 1) явная транзакция у DbContext
await using var tx = await db.Database.BeginTransactionAsync(ct);
try
{
    db.Orders.Add(order);
    await db.SaveChangesAsync(ct);
    await tx.CommitAsync(ct);
}
catch
{
    await tx.RollbackAsync(ct);
    throw;
}

// 2) амбиентная транзакция (охватывает несколько DbContext / вызовов)
using var scope = new TransactionScope(TransactionScopeAsyncFlowOption.Enabled);
Главная мысль

Транзакция в .NET — это арендованное соединение из пула + снимок/блокировки в СУБД. Чем дольше она открыта, тем дольше заняты оба ресурса. Всё остальное — следствия.

Что ломается под нагрузкой

Опасный код выглядит безобидно: транзакция открыта «чтобы всё было атомарно», а внутри — обращения к другим сервисам:

// ✘ соединение занято всё время транзакции, включая сетевые ожидания
await using var tx = await db.Database.BeginTransactionAsync(ct);

db.Orders.Add(order);
await db.SaveChangesAsync(ct);

await _paymentClient.ChargeAsync(order.Id, ct);      // 300 мс … 3 с по сети
await _notifier.SendAsync(order.Id, ct);             // ещё 200 мс

await tx.CommitAsync(ct);
Что происходитЧем это грозит
Соединение занято всё время транзакцииПул исчерпывается: остальные запросы ждут в очереди, получают Timeout expired … obtaining a connection, сервис «встаёт» целиком
В PostgreSQL висит idle in transactionСоединение ничего не делает, но держит снимок: autovacuum не может убрать мёртвые версии → растёт bloat (вопрос 7)
Блокировки строк держатся до коммитаДругие транзакции по тем же строкам ждут → рост задержки, при разном порядке захвата — deadlock detected
Внешний вызов уже сделан, а коммит упалНесогласованность: платёж прошёл, заказ не сохранён. Транзакция БД тут не защищает
TransactionScope + асинхронные вызовыПри подключении второго ресурса — попытка двухфазного коммита (DTC), что в контейнерах и облаке часто просто не работает
Ключевая мысль

Транзакция БД не делает «атомарным» вызов внешнего сервиса. Она лишь удерживает соединение и блокировки — то есть переносит проблему согласованности внутрь базы, попутно создавая проблему с ресурсами.

Как правильно структурировать код

Правило, которое стоит произнести на интервью: транзакция охватывает только работу с БД. Всё, что можно сделать до неё, делается до; всё, что можно отправить после, отправляется после — но надёжно (это и есть Transactional Outbox, вопрос 10).

// ✔ 1. Подготовка — вне транзакции
Validate(order);
var total = await _pricing.CalculateAsync(order, ct);   // расчёты, внешние чтения
order.Total = total;

// ✔ 2. Короткая транзакция: только запись
await using var tx = await db.Database.BeginTransactionAsync(ct);
db.Orders.Add(order);
db.Outbox.Add(OutboxMessage.For(order));                 // событие — в ту же транзакцию
await db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);

// ✔ 3. Побочные действия — после коммита, асинхронно и с повторами
await _bus.PublishPendingAsync(ct);                      // отправляет то, что в outbox
  • Держите транзакцию короткой: чем меньше миллисекунд между BeginTransaction и Commit, тем меньше занятых соединений и блокировок.
  • Оптимистичный параллелизм вместо длинных блокировок: версия строки (xmin в PG, rowversion в EF Core) + повтор при конфликте. Читатели и писатели не ждут друг друга.
  • Атомарные команды вместо «прочитал-изменил-записал»: UPDATE … SET qty = qty - 1 WHERE id = :id AND qty > 0 или INSERT … ON CONFLICT — одна команда, одна короткая блокировка.
  • SELECT … FOR UPDATE — только когда реально нужна пессимистичная блокировка, и только на конкретные строки (не на всю таблицу).
  • Защитные таймауты: SET LOCAL lock_timeout = '2s', statement_timeout, а на стороне PG — idle_in_transaction_session_timeout, чтобы «залипшая» транзакция убивалась сама.
  • Повтор при ошибках сериализации: коды 40001 (serialization_failure) и 40P01 (deadlock_detected) — это нормальные «повтори ещё раз», их обрабатывают ретраем, а не падением запроса.
Ограничение, о котором надо сказать

Если данные лежат в двух системах (БД + брокер, или две БД), «настоящей» транзакции между ними нет. Вместо двухфазного коммита используют компенсации и outbox: в одной транзакции меняем состояние и пишем событие, а отправляем его отдельным воркером.

Что смотреть в мониторинге

Проблему с длинными транзакциями видно в самой СУБД, а не только в .NET:

-- транзакции, которые ничего не делают, но держат снимок и блокировки
SELECT pid, state, now() - state_change AS idle_for,
       now() - xact_start          AS xact_age,
       left(query, 60)             AS last_query
FROM pg_stat_activity
WHERE state = 'idle in transaction'
ORDER BY xact_age DESC;

-- кто кого блокирует прямо сейчас
SELECT blocked.pid AS blocked_pid, blocked.query AS blocked_query,
       blocking.pid AS blocking_pid, blocking.query AS blocking_query
FROM pg_stat_activity blocked
JOIN pg_locks bl ON bl.pid = blocked.pid AND NOT bl.granted
JOIN pg_locks kl ON kl.locktype = bl.locktype
                AND kl.relation IS NOT DISTINCT FROM bl.relation
                AND kl.granted
JOIN pg_stat_activity blocking ON blocking.pid = kl.pid
WHERE blocked.pid <> blocking.pid;
  • Соединения к БД: в Npgsql пул ограничен Max Pool Size (по умолчанию 100). Считайте бюджет: Max Pool Size × число инстансов ≤ max_connections − запас для администрирования и реплик. Иначе инстансы «съедят» лимит сервера.
  • Метрики пула: db.client.connections.usage (Npgsql отдаёт их через ActivitySource/EventCounters): сколько свободных, сколько занято, сколько запросов ждут.
  • Признак в логах: Timeout expired. The timeout period elapsed prior to obtaining a connection from the pool — почти всегда это не «мало соединений», а «слишком долго держим».
  • Защита на стороне сервера: idle_in_transaction_session_timeout (например, 30–60 с) — база сама прибьёт «залипшую» транзакцию, и её будет видно в логах как FATAL: terminating connection due to idle-in-transaction timeout.

Готовый ответ

Как вы управляете транзакциями в .NET при сложной логике?

«Транзакция у меня охватывает только работу с БД. Всё, что требует сети — расчёты, обращения к внешним сервисам, отправку уведомлений — я выношу до или после транзакции. Внутри: BeginTransactionAsync, изменения, SaveChangesAsync, CommitAsync — миллисекунды, а не секунды. Если изменения затрагивают две системы, я не пытаюсь соединить их одной транзакцией: пишу событие в outbox в той же транзакции, а доставку делает отдельный воркер.»

К каким проблемам приводит транзакция с внешними вызовами внутри?

«Первое — пул соединений: соединение занято всё время, включая сетевые ожидания, и при нагрузке пул исчерпывается — остальные запросы падают с pool timeout. Второе — в PostgreSQL такие транзакции висят как idle in transaction: они держат снимок, мешают autovacuum убирать мёртвые версии (растёт bloat) и держат блокировки строк до самого коммита, отсюда рост задержки и deadlock’и. Третье — согласованность всё равно не гарантируется: внешний сервис уже всё сделал, а коммит может упасть. И если подключится второй транзакционный ресурс, TransactionScope потянет двухфазный коммит, который в контейнерной среде обычно недоступен.»

Как минимизировать время удержания соединения?

«Четыре приёма. Первый — читать и считать вне транзакции, внутри только запись. Второй — вместо «прочитал-изменил-записал» использовать одну атомарную команду (UPDATE … WHERE qty > 0, INSERT … ON CONFLICT) — блокировка строки живёт микросекунды. Третий — оптимистичный параллелизм по версии строки вместо пессимистичных блокировок, с повтором на 40001/40P01. Четвёртый — защитные таймауты: lock_timeout и statement_timeout на транзакцию плюс idle_in_transaction_session_timeout на сервере. И обязательно смотрю pg_stat_activity и метрики пула, чтобы это не оставалось теорией.»
