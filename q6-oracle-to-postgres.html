Oracle → PostgreSQL: MVCC, блокировки и конвертация PL/SQL

Чем отличаются механизмы согласованности в двух СУБД, как ведут себя блокировки при чтении и записи и что делать с фичами Oracle без прямого аналога.

Алексей Грознов · миграция корпоративных БД Oracle → PostgreSQL (DBA2, DBA3, QPT)

Вопрос 6. MVCC: Oracle и PostgreSQL

Идея MVCC в обеих СУБД одна: читатель видит согласованный снимок данных и не блокирует писателя, а писатель не блокирует читателя. Различие — в том, где хранятся старые версии строк, и это меняет поведение системы.

Oracle

  • MVCC реализован через undo: актуальные данные — в таблицах, прошлые версии — в undo-табличном пространстве.
  • Читатель получает снимок по SCN (system change number).
  • Если undo «перезаписался», долгий запрос может получить ORA-01555: snapshot too old.

PostgreSQL

  • MVCC реализован в самих страницах таблицы: у каждой версии строки есть метки видимости (xmin/xmax).
  • При UPDATE создаётся новая версия строки, старая остаётся, пока её не уберёт VACUUM.
  • Обратная сторона: bloat (раздувание) и важность autovacuum; долгие транзакции мешают очистке.

Что важно на практике

После перехода на PostgreSQL нужно настроить autovacuum, не держать длинные транзакции и следить за bloat: интенсивные UPDATE/DELETE плодят версии, и без очистки таблицы и индексы «толстеют».

Блокировки при чтении и записи

Чтение

  • В обеих СУБД SELECT не блокируется чужими изменениями.
  • В PostgreSQL SELECT берёт ACCESS SHARE, который конфликтует с DDL: ALTER TABLE / TRUNCATE берут ACCESS EXCLUSIVE.
  • В Oracle DDL авто-коммитится; в PostgreSQL DDL транзакционный.

Запись

  • Блокировка на уровне строки; второй писатель той же строки ждёт.
  • Читатели строку не блокируют — видят прежнюю версию.
  • Есть SELECT ... FOR UPDATE; deadlock обе системы обнаруживают — отменённую транзакцию нужно повторить (retry).

Что «блокирует» таблицу в PostgreSQL

ALTER TABLE, TRUNCATE, VACUUM FULL, CREATE INDEX (без CONCURRENTLY), CLUSTER. Поэтому в продакшене — короткие транзакции и CREATE INDEX CONCURRENTLY.

Уровни изоляции

  • По умолчанию в обеих — READ COMMITTED.
  • Oracle SERIALIZABLE = snapshot isolation; PostgreSQL SERIALIZABLE строже (SSI).
  • 40001 (serialization failure) и deadlock в PostgreSQL — норма: критичные транзакции оборачивают в retry.

Конвертация специфичных фич Oracle

1. NULL и пустая строка — самое известное различие

В Oracle пустая строка '' и NULL — это одно и то же. В PostgreSQL '' — обычная пустая строка. Это ломает логику:

  • проверки IS NULL не срабатывают для пустых строк;
  • NOT NULL в PostgreSQL пропустит пустую строку (в Oracle — нет);
  • уникальность: в Oracle '' = NULL, а NULL-ы в уникальном индексе допустимы; в PostgreSQL NULL-ы по умолчанию различны (меняется через NULLS NOT DISTINCT, PG15+);
  • конкатенация: NULL || 'x' в Oracle даёт 'x', в PostgreSQL — NULL.
Что делали

Приводили данные при миграции (пустые строки → NULL там, где так было в Oracle), добавляли CHECK (col <> '') или NULLIF(col,'') и переписывали проверки в коде. Ошибки тут «тихие» — проявляются не сразу, поэтому это ловят тестами эквивалентности.

2. PACKAGE — прямого аналога нет

Пакет в Oracle — это группа процедур/функций плюс состояние сессии (package variables). В PostgreSQL пакетов нет. Варианты:

  • Схема как пространство имён — функции группировали в схему (pkg_orders.calculate_total(...)).
  • Префиксы в именах функций/процедур.
  • Состояние сессии эмулировали через временные таблицы или set_config/GUC — либо (правильнее) убирали глобальное состояние.
  • В PostgreSQL 11+ есть настоящие процедуры (CREATE PROCEDURE) с управлением транзакциями.

3. PRAGMA AUTONOMOUS_TRANSACTION

Нужна, когда операция (аудит/лог) должна зафиксироваться независимо от основной транзакции — даже если основная откатится. В PostgreSQL функции так транзакциями не управляют.

  • Обходной путь: отдельное соединение — расширение dblink (или background worker): своя сессия, значит своя транзакция.
  • Архитектурно лучше: вынести аудит/логирование из транзакции — писать события в очередь (таблица-очередь + фоновый воркер) или в отдельную лог-систему.
  • Честная формулировка: «точного аналога нет; где-то использовали dblink, где-то меняли архитектуру, чтобы лог не зависел от основной транзакции».

Ещё несколько «коварных» мест

  • Регистр идентификаторов: Oracle хранит имена в верхнем регистре, PostgreSQL — в нижнем; код с кавычками может «не найти» объект.
  • Порядок NULL при сортировке: лучше указывать NULLS LAST/FIRST явно.
  • Автокоммит DDL: в Oracle DDL фиксируется сам, в PostgreSQL — часть транзакции.
  • Неявные преобразования: в PostgreSQL строже — часть «магии» Oracle просто не скомпилируется (что скорее хорошо: ошибки видны сразу).

План миграции (как делали по шагам)

  1. Инвентаризация. Переписать все объекты БД: таблицы, представления, индексы, последовательности, триггеры, пакеты/процедуры/функции, задания, внешние связи.
  2. Маппинг типов и конвертация схемы. Oracle-типы → PostgreSQL (особенно DATE → timestamp, NUMBER → numeric/bigint).
  3. Конвертация PL/SQL. Пакеты → схемы с функциями; автономные транзакции → dblink или смена архитектуры; функции/триггеры → PL/pgSQL. Часть — автоматически, часть — вручную.
  4. Миграция данных. Перенос, setval для последовательностей, проверка объёмов и контрольных сумм.
  5. Тесты эквивалентности. Одни и те же запросы/отчёты прогоняли на Oracle и PostgreSQL и сравнивали результаты. Это ловило и ''-vs-NULL, и порядок NULL, и ошибки в ROWNUM-логике.
  6. Сравнение производительности. Планы и замеры на сопоставимых объёмах; подгонка индексов и статистики.
  7. Настройка PostgreSQL. autovacuum, work_mem, random_page_cost под SSD, статистика, мониторинг (pg_stat_statements, bloat, locks).
  8. Поэтапное переключение с возможностью отката.
★ Готовый ответ по Вопросу 4 (сжато)

«MVCC в обеих СУБД даёт главное: читатели не блокируют писателей. Различие — где хранятся прошлые версии. В Oracle — в undo, снимок по SCN; в PostgreSQL — прямо в страницах таблиц (xmin/xmax), а старые версии убирает VACUUM. Отсюда специфика PostgreSQL: bloat, важность autovacuum и влияние долгих транзакций. По блокировкам: изменение — на уровне строки, чтение никого не блокирует, но DDL в PostgreSQL конфликтует с чтениями — поэтому используем CREATE INDEX CONCURRENTLY и retry на сериализационные ошибки. По конвертации труднее всего дались: '' ≠ NULL, отсутствие PACKAGE (группировали в схемы) и автономных транзакций (dblink или вынос логов из транзакции), а также DATE, который в Oracle содержит время. Плюс массовая замена NVL/DECODE/ROWNUM/(+)/CONNECT BY».

Что подчеркнуть про свой опыт

Миграция — это не «перенести данные», а перенести поведение: типы, семантику NULL, логику в коде БД и производительность. Тесты эквивалентности и замеры — в центре процесса: только так ловятся «тихие» расхождения.
