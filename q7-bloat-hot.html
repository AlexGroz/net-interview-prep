Раздувание таблиц, HOT-апдейты и роль fillfactor

Почему интенсивные UPDATE и DELETE «раздувают» таблицы и индексы, как встроенный HOT-механизм этого избегает и что нужно сделать в схеме и в коде, чтобы база не деградировала.

Алексей Грознов · PostgreSQL (QPT, DBA2, DBA3), высоконагруженные сервисы на .NET

Откуда берётся bloat

В PostgreSQL UPDATE не меняет строку на месте: создаётся новая версия строки, а старая помечается мёртвой и ждёт, пока её уберёт VACUUM (это цена MVCC — главы 21 и 25 SQL-раздела). DELETE — то же самое: строка не исчезает, а становится мёртвой версией.

Если версии не успевают убираться, файлы таблицы и индексов растут быстрее, чем реальные данные. Это и есть bloat — «раздувание». Последствия:

  • таблица и индексы занимают больше места (а значит, больше страниц читается — растёт I/O);
  • индекс становится «мягким»: больше страниц на тот же объём данных, хуже кэшируется;
  • autovacuum работает дольше и чаще, добавляя нагрузку;
  • в крайних случаях планы перестают использовать индекс (планировщик считает Seq Scan дешевле).
Как это формулировать

«Bloat — это пространство, занятое мёртвыми версиями строк и «дырками» в страницах. Таблица при этом отдаёт те же данные, но за большее число страниц, поэтому запросы дорожают, а autovacuum не справляется.»

HOT-апдейты и fillfactor

HOT (Heap-Only Tuples) — встроенная оптимизация PostgreSQL: если при UPDATE новая версия строки помещается в ту же страницу и ни одно из изменённых полей не входит в индекс, то записи в индексы не создаются вообще. Новая версия просто прицепляется к цепочке в странице (HOT chain).

Отсюда два условия HOT — их и надо назвать на интервью:

  1. Меняемые колонки не индексированы. Если обновляется колонка, которая есть хотя бы в одном индексе, PostgreSQL обязан обновить индекс → HOT невозможен.
  2. На странице есть свободное место. Если страница заполнена полностью, новую версию положить некуда, и строка уходит в другую страницу.

Второе условие решается fillfactor — процентом заполнения страниц при записи. Для «горячих» таблиц ставят 80–90 %: часть страницы заранее оставляют пустой, чтобы будущим версиям было куда лечь.

-- таблица, которую часто обновляют
ALTER TABLE orders SET (fillfactor = 85);

-- при пересоздании/переупаковке таблицы
CREATE INDEX idx_orders_status ON orders (status) WITH (fillfactor = 90);
Главная ловушка

Индекс на «живой» колонке — например updated_at или status, который меняется на каждом шаге процесса, — отключает HOT и заставляет писать в индекс при каждом UPDATE. Тогда «миллионы UPDATE в сутки» превращаются в миллионы новых индексных записей и рост bloat индексов.

Как диагностировать

Сначала — статистика по таблицам. Если n_dead_tup растёт, а n_tup_hot_upd близок к нулю при большом n_tup_upd, значит HOT не работает:

SELECT relname,
       n_live_tup, n_dead_tup,
       n_tup_upd, n_tup_hot_upd,          -- HOT-обновления: чем больше доля, тем лучше
       n_tup_del,
       last_vacuum, last_autovacuum,
       pg_size_pretty(pg_total_relation_size(relid)) AS total_size
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC
LIMIT 20;

-- доля HOT-апдейтов: близко к 1 — схема «дружелюбна» к HOT
SELECT relname,
       round(n_tup_hot_upd::numeric / GREATEST(n_tup_upd, 1), 2) AS hot_ratio,
       round(n_dead_tup::numeric / GREATEST(n_live_tup, 1), 2)   AS dead_ratio
FROM pg_stat_user_tables
WHERE n_tup_upd > 0
ORDER BY n_dead_tup DESC LIMIT 20;
  • Точный размер bloat — расширение pgstattuple: SELECT * FROM pgstattuple('orders'); даёт долю мёртвых кортежей и «свободного» пространства; для индексов — pgstatindex('idx_orders_created_at').
  • Аппроксимация без расширений — сравнить «ожидаемый» размер (число строк × средняя ширина) с фактическим pg_total_relation_size, или воспользоваться известными bloat-запросами из wiki.
  • История обслуживания — last_autovacuum и настройки autovacuum_vacuum_scale_factor: для большой таблицы «20 % изменённых строк» — это очень много, поэтому порог часто занижают на уровне таблицы.

Как лечить

  • Дать autovacuum работать вовремя. Для больших «горячих» таблиц пороги по умолчанию слишком грубые (20 % строк). Их сужают на уровне таблицы:
ALTER TABLE orders SET (
    autovacuum_vacuum_scale_factor  = 0.01,   -- 1% изменённых строк вместо 20%
    autovacuum_vacuum_threshold     = 1000,
    autovacuum_vacuum_cost_limit    = 2000,   -- не душить очистку по стоимости
    autovacuum_analyze_scale_factor = 0.005
);
  • fillfactor 80–90 % для таблиц с частыми UPDATE — место под новые версии прямо в странице (условие HOT).
  • Дружить с HOT по схеме: не индексировать колонки, которые меняются на каждом шаге; вычистить лишние индексы (каждый индекс — это дополнительная запись на каждый UPDATE); историю статусов вынести в отдельную таблицу-журнал.
  • Партиционирование вместо массовых DELETE (вопрос 8): удаление старых данных — это DETACH PARTITION / DROP TABLE за миллисекунды, без миллионов мёртвых версий.
  • Убирать существующий bloat: pg_repack — пересобирает таблицу без длительной блокировки, VACUUM FULL — возвращает место ОС, но берёт ACCESS EXCLUSIVE (только в окно обслуживания), REINDEX CONCURRENTLY — для раздутых индексов.
  • Не мешать очистке: долгие транзакции и idle in transaction держат горизонт, и VACUUM не может удалить версии, которые ещё «видны» этой транзакции. Связь с вопросом 4 прямая.

Что зависит от .NET-кода

Приложение может либо помогать базе, либо мешать — и это заметно именно на интенсивной записи:

// ✘ «На каждом шаге процесса» трогаем индексируемую колонку — HOT отключается
order.UpdatedAt = DateTime.UtcNow;      // и на updated_at висит индекс
await db.SaveChangesAsync(ct);

// ✔ Массовое изменение — одной командой, без загрузки сущностей и лишних колонок
await db.Orders
    .Where(o => o.Status == OrderStatus.New && o.CreatedAt < cutoff)
    .ExecuteUpdateAsync(s => s.SetProperty(o => o.Status, OrderStatus.Expired), ct);

// ✔ Удаление старых данных — тоже одной командой и батчами, а не «всё сразу»
await db.Orders.Where(o => o.CreatedAt < cutoff).ExecuteDeleteAsync(ct);
  • EF Core пишет только изменённые колонки для отслеживаемых сущностей — это помогает HOT. Но если пометить сущность как Modified целиком или «приаттачить» её, уйдёт UPDATE по всем колонкам.
  • ExecuteUpdate/ExecuteDelete не загружают данные в память — один SQL, меньше изменённых колонок, меньше мёртвых версий на клиенте.
  • Репозиторий не должен обновлять «всё поле целиком», если меняется одно значение — экономим и запись, и индексы.
  • Чтение — без трекинга (AsNoTracking), а для тяжёлой загрузки — COPY/NpgsqlBinaryImporter: меньше транзакций и мёртвых версий.
  • Долгие транзакции — враг очистки. Если приложение держит открытую транзакцию, пока «докручивает» бизнес-процесс, autovacuum физически не может убрать версии (вопрос 4).

Готовый ответ

Что такое Bloat и как вы его диагностируете?

«Bloat — это «раздувание» таблиц и индексов. В PostgreSQL UPDATE не меняет строку на месте: создаётся новая версия, а старая остаётся мёртвой до тех пор, пока её не уберёт VACUUM. При интенсивной записи файлы растут быстрее данных, страницы читаются «вхолостую», autovacuum начинает не успевать, а индексы становятся «мягкими». Диагностирую по pg_stat_user_tables: смотрю n_dead_tup, n_tup_upd и n_tup_hot_upd, а также last_autovacuum и размер таблицы; точные цифры даёт pgstattuple для таблиц и pgstatindex для индексов. Дальше смотрю, не держат ли горизонт долгие транзакции и idle in transaction — при них VACUUM не может удалять версии.»

Что такое HOT-апдейты и при каких условиях они работают?

«HOT (Heap-Only Tuples) — это когда при UPDATE новые версии строк не создают новых записей в индексах. Условий ровно два: ни одна из изменяемых колонок не входит ни в один индекс, и новая версия помещается в ту же страницу. Второе условие обеспечивает fillfactor: для «горячих» таблиц его снижают до 80–90 %, оставляя место под новые версии. Если же на часто обновляемой колонке (например, status или updated_at) висит индекс, HOT не работает вообще — и каждый UPDATE тянет за собой запись в индекс. Поэтому я не индексирую то, что меняется постоянно, и убираю лишние индексы.»

Что можно сделать, чтобы .NET-приложение не «убивало» базу?

«Три вещи. На стороне схемы: fillfactor, заниженные пороги autovacuum для конкретных таблиц, HOT-дружелюбный набор индексов, а для удаления старых данных — партиционирование, чтобы удалять секции, а не писать миллионы DELETE. На стороне кода: массовые изменения делать через ExecuteUpdate/ExecuteDelete и батчами, читать через AsNoTracking, а транзакции держать короткими. И обязательный мониторинг: доля HOT-апдейтов, мёртвые кортежи, дата последнего autovacuum — по ним сразу видно, что приложение начинает вредить.»
