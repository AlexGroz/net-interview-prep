Секционирование больших таблиц и partition pruning

Зачем делить таблицу на секции, по какому ключу выбирать Range / List / Hash и почему запрос из .NET может заставить PostgreSQL читать все секции вместо одной.

Алексей Грознов · миграция терабайтных таблиц, PostgreSQL, EF Core

Что такое декларативное секционирование

Секционирование — это когда одна «логическая» таблица физически состоит из множества таблиц-секций (PostgreSQL 10+). Секции не пересекаются и определяются ключом секционирования: по диапазону, по списку значений или по хэшу.

CREATE TABLE orders (
    id         bigint      NOT NULL,
    created_at timestamptz NOT NULL,
    user_id    uuid        NOT NULL,
    status     text        NOT NULL,
    PRIMARY KEY (id, created_at)          -- ключ секционирования обязан входить в PK/уникальные ключи
) PARTITION BY RANGE (created_at);

CREATE TABLE orders_2026_01 PARTITION OF orders
    FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');
CREATE TABLE orders_2026_02 PARTITION OF orders
    FOR VALUES FROM ('2026-02-01') TO ('2026-03-01');

-- «страховка» от ошибок вставки: секция для всего остального
CREATE TABLE orders_default PARTITION OF orders DEFAULT;
СтратегияКогда выбираютПример
RANGEДанные растут во времени, старые уходят целикомпо created_at — месяц/день/год
LISTОграниченный набор значений (арендатор, регион, тип)по tenant_id или region
HASHРавномерное распределение, когда естественного ключа нетпо user_id на 16 секций
СубсекционированиеНужны две оси (например, время + арендатор)RANGE по дате → LIST по региону
Главный критерий выбора ключа

Ключ должен совпадать с тем, по чему фильтруют почти все запросы (обычно дата) и что удобно удалять целиком. Если секционировать «наугад», запросы будут читать все секции — то есть станет хуже, чем было.

Что даёт секционирование

  • Partition pruning — планировщик отбрасывает секции, которые не могут содержать подходящих строк. Запрос «за январь» читает одну секцию вместо сотни.
  • Дешёвое удаление старых данных — вместо DELETE на миллионы строк (и миллионов мёртвых версий) делается DETACH PARTITION или DROP TABLE: миллисекунды и никакого bloat.
  • Обслуживание по частям — VACUUM и ANALYZE идут по отдельным (меньшим) секциям, а статистика по свежим данным точнее.
  • Меньше индексов на диске — у каждой секции свой B-tree; при большом числе вставок это заметно дешевле одного гигантского индекса.
  • Гибкость размещения — холодные секции можно держать на «медленных» дисках, горячие — на быстрых (tablespace).
Чего секционирование не делает

Оно не ускоряет запрос, который не фильтрует по ключу секционирования. И у него есть цена: больше объектов в каталоге, требуется управление секциями (создание заранее, обслуживание границ) и аккуратность с уникальными ключами.

Partition pruning: когда работает, а когда нет

Pruning — оптимизация на этапе планирования: PostgreSQL сравнивает условие на колонку-ключ с границами секций и выкидывает лишние. Чтобы это сработало, условие должно быть простым сравнением колонки с константой и типы должны совпадать.

Условие в запросеPruningПочему
created_at >= '2026-01-01' AND created_at < '2026-02-01'даСравнение колонки с константами того же типа
created_at >= now() - interval '1 day'да*Функция стабильная, но значение вычисляется один раз на запрос
date(created_at) = '2026-01-15'нетФункция по колонке — планировщик не знает границ
created_at::text LIKE '2026-01%'нетПриведение колонки к другому типу
created_at = $1, но параметр передан как textзависитНесовпадение типов мешает сопоставить границы
Условие в JOIN подзапроса, вычисленное во время выполнениячасто нетГраницы неизвестны на этапе планирования

Отдельный практический момент — параметризованные запросы (как раз то, что генерирует EF Core). У PostgreSQL есть выбор между планом «под конкретные значения» и «общим» (generic) планом для prepared statement. Обычно pruning работает и с параметрами, но если тип параметра «размылся» (например, приходит строка), отсечение теряется.

Ошибки со стороны .NET, из-за которых читаются все секции

Типовая причина «Seq Scan по всем секциям» — функция или приведение к колонке-ключу, появившиеся в LINQ. Планировщик видит не колонку, а выражение и уже не может отбросить секции.

// ✘ функция по колонке: date(year FROM created_at) = 2026 → все секции
var bad1 = await db.Orders.Where(o => o.CreatedAt.Year == 2026).ToListAsync();

// ✘ приведение к дате: created_at::date = '2026-01-15' → все секции
var bad2 = await db.Orders.Where(o => o.CreatedAt.Date == day).ToListAsync();

// ✘ строка как параметр: сравнение с text вместо timestamptz
var bad3 = await db.Orders
    .FromSqlInterpolated($"SELECT * FROM orders WHERE created_at::text LIKE {prefix + \"%\"}")
    .ToListAsync();

// ✔ диапазон: сравнение колонки с типизированными границами → одна секция
var from = new DateTime(2026, 1, 1, 0, 0, 0, DateTimeKind.Utc);
var to   = from.AddMonths(1);
var good = await db.Orders
    .Where(o => o.CreatedAt >= from && o.CreatedAt < to)
    .ToListAsync();
  • Фильтр «не по ключу» — тоже чтение всех секций. Если таблица секционирована по дате, а запрос идёт «по user_id», секции не отбросить (в PG индексы у секционных таблиц локальные). В таком случае ключ выбирают иначе — например, субсекционирование по пользователю.
  • Contains по списку работает нормально, но только если условие сравнивает именно колонку-ключ и список типизирован (List<DateTime>, а не строки).
  • Значение DateTime и Kind: для timestamptz передавайте UTC — иначе значение «поедет», и данные могут уйти не в ту секцию (или вообще в DEFAULT).
  • Проверяйте SQL, а не LINQ: ToQueryString() сразу показывает, появилась ли функция по колонке.

Как проверить, что pruning действительно работает

-- секционировано по месяцам, фильтр «за январь»

✘ pruning нет:
Append  (cost=…)
  -> Seq Scan on orders_2026_01  …
  -> Seq Scan on orders_2026_02  …      ← читаем 12 секций
  …
  -> Seq Scan on orders_2026_12  …

✔ pruning есть:
Append  (cost=…)
  Subplans Removed: 11                  ← 11 секций отброшено планировщиком
  -> Index Scan using orders_2026_01_created_at_idx on orders_2026_01 …
  • Subplans Removed — прямая метрика отсечения; в EXPLAIN (ANALYZE) дополнительно видно, сколько строк реально прочитано из каждой секции.
  • BUFFERS — сколько страниц запрос «потрогал». Если читается вся таблица, shared read будет огромным, независимо от того, что вернулось мало строк.
  • Статистика по секциям: в pg_stat_user_tables растут seq_scan/seq_tup_read у всех секций — значит, отсечения нет.
  • pg_stat_statements — какие запросы дают наибольший I/O; полезно сопоставить с тем, что генерирует приложение (там же видно нормализованный SQL).
  • auto_explain — пишет план медленных запросов в лог: удобно ловить «внезапно ставшие полными» сканирования в проде.

Практика: как это делается и как живёт с EF Core

  • Секции создаются заранее. Никто не создаёт их «по требованию из приложения»: это делает отдельное задание (например, pg_partman) — оно же и удаляет старые. Если секции закончились, строки уйдут в DEFAULT, и запросы начнут читать её целиком.
  • Удаление старых данных — это DETACH PARTITION (с CONCURRENTLY, чтобы не блокировать) и затем DROP TABLE уже отсоединённой секции. Никаких миллионов удаляемых строк и никакого bloat.
  • Индексы создаются на родительской таблице — PostgreSQL создаёт их на всех существующих секциях и на будущих. Уникальные ключи обязаны включать ключ секционирования (PRIMARY KEY (id, created_at)).
  • Загрузка больших объёмов при миграции: сначала наполняем обычную таблицу, а потом ALTER TABLE orders ATTACH PARTITION orders_2026_01 FOR VALUES FROM (…) TO (…) — это быстрее и безопаснее, чем вставлять миллионы строк в уже партиционированную таблицу.
EF Core и секционирование

EF Core не управляет секциями: это забота БД. В модели таблица просто маппится на родителя, запросы и вставки работают как с обычной таблицей. Создание секций и индексов делают SQL-скрипты в миграциях:

// EF Core-миграция: секционирование задаётся обычным SQL
migrationBuilder.Sql(@"
    ALTER TABLE orders SET (fillfactor = 85);
    CREATE TABLE IF NOT EXISTS orders_2026_03 PARTITION OF orders
        FOR VALUES FROM ('2026-03-01') TO ('2026-04-01');
");
// помните: CREATE TABLE ... PARTITION OF нельзя выполнять внутри транзакции,
// где уже менялась схема — в PG это часть DDL-ограничений

И обязательный чек-лист перед тем, как считать задачу закрытой: секций десятки, а не тысячи; есть DEFAULT-секция или контроль за созданием новых; настроено удаление старых; горячие запросы проверены на отсечение в EXPLAIN.

Готовый ответ

В каких случаях вы выберете секционирование и по какому ключу?

«Секционирование я рассматриваю, когда таблица становится очень большой и по ней есть естественная ось. В подавляющем большинстве случаев это RANGE по дате: данные растут во времени, а старые периоды нужно хранить и потом удалять целиком. Если сущность логически делится по арендатору или региону, беру LIST; если равномерно разложить данные без естественного ключа — HASH. Ключ я выбираю по тому, как фильтруют почти все запросы: иначе секционирование не даёт отсечения и только добавляет накладные расходы. И главный практический выигрыш для меня не столько скорость, сколько обслуживание: удаление старых данных — это DETACH и DROP секции за миллисекунды вместо миллионов DELETE, которые раздувают таблицу и индексы.»

Как планировщик ведёт себя при оптимизации запросов к секционированным таблицам?

«На этапе планирования работает partition pruning: PostgreSQL сопоставляет условие на колонку-ключ с границами секций и отбрасывает неподходящие. В EXPLAIN это видно строкой Subplans Removed. Ключевое условие — сравнение должно быть простым (>=, <, =) и типы должны совпадать. Как только в запросе появляется функция или приведение по колонке-ключу, планировщик теряет информацию о границах — и в плане появляется Append с Seq Scan по всем секциям.»

Какие ошибки в LINQ и SQL приводят к сканированию всех секций?

«Из .NET чаще всего приходят три вещи. Первое — функции по колонке, которые выглядят «естественно» в LINQ: CreatedAt.Year, CreatedAt.Date, ToString().StartsWith(...). Второе — несовпадение типов: дата уходит как строка (text), и условие теряет возможность сопоставления с границами. Третье — фильтр не по ключу секционирования: если таблица секционирована по дате, а запрос по user_id, отсечения не будет вообще, потому что индексы в PostgreSQL локальные. Лечится это просто: передавать типизированные значения (DateTime, Guid) и писать диапазон (>= from AND < to) вместо функций по колонке. И проверять результат через ToQueryString() плюс EXPLAIN (ANALYZE, BUFFERS), а не «на глаз».»
