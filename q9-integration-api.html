REST, gRPC, брокеры сообщений и валидация входных данных

Когда остаться на REST, а когда перейти на gRPC или брокер сообщений — и как организовать валидацию входящих данных в ASP.NET Core.

Алексей Грознов · проектирование API и интеграций (.NET Core / ASP.NET Core)

Часть 1. REST vs gRPC vs брокеры сообщений

REST с JSON удобен, но не бесплатен: текст сериализуется и занимает больше байт. На одном запросе это незаметно, а между сервисами внутри системы вызовов — миллионы. Поэтому выбор определяется задачей, а не «модой».

REST — когда он правильный

  • Кто клиент: браузер, мобильное приложение, внешняя система.
  • Плюсы: читается и легко отлаживается (curl, Postman), работает везде, штатное кэширование по HTTP, не нужна кодогенерация.
  • Берём REST, когда: API публичный или интеграция с чужими системами; важны простота и совместимость, а не экономия байтов.

gRPC — когда выигрывает

  • Кто клиент: свои сервисы.
  • Плюсы: бинарный Protobuf (компактнее и быстрее JSON), HTTP/2 (мультиплексирование в одном соединении), стриминг, строгий контракт из .proto и кодогенерация клиентов.
  • Ограничения: нечитаемо вручную (нет простого curl), браузерам нужна прослойка (gRPC-Web), хуже дружит с прокси и кэшированием.
  • Берём gRPC, когда: много внутренних вызовов, важны задержка и трафик, нужен стриминг.

Брокер сообщений — когда нужна асинхронность

  • Идея: один сервис кладёт сообщение в брокер (RabbitMQ, Kafka), другой забирает и обрабатывает — не одновременно и без ожидания.
  • Плюсы: развязка по времени, сглаживание пиков, надёжность (сообщение не потеряется), масштабирование обработчиков.
  • Что помнить: ответ приходит «потом» (eventual consistency); доставка at-least-once → возможны дубликаты, значит обработчик должен быть идемпотентным; появляется инфраструктура.
  • Берём брокер, когда: работа долгая (отвечаем 202 Accepted), нужно пережить пики, это события для других систем.

REST — на границе с внешним миром, gRPC — внутри между сервисами, брокер — для того, что можно сделать позже (тяжёлые и фоновые задачи).

Часть 2. Валидация входных данных в ASP.NET Core

Правило номер один: клиенту доверять нельзя. Проверки на клиенте нужны только ради удобства (показать ошибку сразу) — сервер проверяет всё сам.

Четыре уровня защиты

  1. Инфраструктурные лимиты: размер тела запроса, rate limiting, таймауты — отсечь «наглое» до логики.
  2. Формат и модель: типы и обязательные поля.
  3. Бизнес-правила: «дата окончания позже начала», «нельзя отменить оплаченный заказ».
  4. Гарантия в БД: NOT NULL, UNIQUE, CHECK, внешние ключи — последний рубеж.

Как это выглядит в коде (MVC/Controller)

public sealed class CreateOrderRequest
{
    [Required]
    [Range(1, int.MaxValue)]
    public int CustomerId { get; init; }

    [Required]
    [StringLength(200, MinimumLength = 3)]
    public string Title { get; init; } = "";

    [Range(0.01, 1_000_000)]
    public decimal Total { get; init; }
}

[ApiController]                 // ← с этим атрибутом модель проверяется автоматически
[Route("api/orders")]
public class OrdersController : ControllerBase
{
    [HttpPost]
    public IActionResult Create(CreateOrderRequest request)
    {
        // если модель невалидна — сюда не попадём: вернётся 400 с описанием
        return Ok(_service.Create(request));
    }
}

В Minimal API авто-проверки нет: валидируем вручную или через endpoint-фильтр (а для сложных правил подключаем FluentValidation — отдельный класс-валидатор).

Нет прав403

Что чаще всего делают неправильно
  • Отдают 500 на некорректный ввод — путают клиента и мониторинг.
  • Принимают сущность БД вместо DTO → клиент может перезаписать лишние поля (защита от over-posting).
  • Не ограничивают размер тела запроса — сервис можно «залить».
  • Логируют то, что вернули в ошибке (пароли, персональные данные).

Готовый ответ (сжато)

Про REST / gRPC / брокеры. «Выбираю по трём вопросам: кто клиент, нужен ли ответ сейчас и насколько интенсивный обмен. Публичный API — REST: понятно, отлаживается curl, кэшируется, работает в браузере. Внутренние вызовы — gRPC: бинарный Protobuf и HTTP/2 дают меньше трафика и задержку, плюс стриминг и строгий контракт. Долгие и пиковые операции — брокер: клиенту отвечаем 202 Accepted, работу делает воркер; там же нужна идемпотентность, потому что доставка «хотя бы один раз». На практике используют всё три: REST снаружи, gRPC внутри, брокер для событий».

Про валидацию. «Валидация у меня на нескольких уровнях. Сначала инфраструктурные лимиты: размер тела, rate limiting, таймауты. Затем формат и модель — атрибуты на DTO плюс [ApiController], для сложных правил FluentValidation. Бизнес-правила — в сервисном слое. Гарантию дают ограничения в БД: NOT NULL, UNIQUE, CHECK. Плохой ввод возвращаю как 400/422 с описанием, никогда не 500. И принимаю DTO, а не сущности БД — чтобы клиент не мог перезаписать лишние поля».
